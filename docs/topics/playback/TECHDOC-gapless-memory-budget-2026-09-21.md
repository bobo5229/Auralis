# TECHDOC：无缝播放解码前的内存预算与回退

状态：已实施，定向验证通过；真实音频边界及内存峰值未验证。日期：2026-09-21。

## 实施记录（2026-09-21）

- 播放资源契约返回可选探测信息；Main 使用现有解析器，最多输入 1 MiB，关闭封面及全文件时长扫描，128 项指纹缓存。仅对 WAV、FLAC、MP3、M4A 尝试有界探测；Ogg/ADTS 等可能返回局部帧时长的路径直接回退。
- 首曲和预加载共同使用 512 MiB 准入预算，计入持有 buffer（按对象去重）、两份编码数据、预计 PCM 和一份等量解码余量；保留解码后检查。策略未经 RSS 测量，不是进程硬上限。
- 单引擎最多一个活动准备任务；不可取消的旧解码直到 finally 才释放预留。取消、暂停、销毁和 resume 竞态通过 generation 拦截。
- 流式读取限制为已探测文件大小，同时受编码上限约束；自定义音频协议支持指纹头及 CORS preflight，陈旧指纹在正文返回前拒绝。
- 普通定向测试 49 项通过（预算/引擎 17、runtime 8、controller 6、探测 2、受接线影响的 usePlayback 16），Electron 音频协议 7 项通过。隔离 WAV 大于 1 MiB 的完整时长探测和缓存失效通过；当前曲目结束后迟到的预解码结果丢弃测试通过。
- Main `tsc`、`npm.cmd exec -- electron-vite build` 通过。完整 `typecheck` 仍因专辑调色板两处错误及既有智能歌单测试导入失败；未宣称完整 `npm.cmd run build` 通过。
- 未进行真实听感、无缝边界、HTMLAudio 实播及 Renderer 内存峰值验证；Mock 仅证明调用和生命周期。源文件在协议检查后仍可能变化，底层解码器分配无法由该预算完全约束。下文保留原始设计依据。

## 问题与证据

`GaplessAudioEngine.prepare` 先调用 `decodeAudioData`，再检查时长、单曲 PCM 和总 PCM。当前限制分别为编码数据 256 MiB、单曲 PCM 320 MiB、缓冲 PCM 512 MiB、时长两小时。
解码后检查只能拒绝保留结果，无法阻止解码期间的大分配。文件压缩大小也不能可靠约束 PCM；例如两小时、48 kHz、双声道 Float32 PCM 约为 2.57 GiB，尚未包含编码输入和解码临时内存。

同时，当前总量计算只包含 current 与新结果，没有覆盖旧 next 或尚未完成的解码。AbortController 可以取消读取，却不能据此认定已开始的解码被取消。
缺少 Content-Length 时，当前 `arrayBuffer()` 也会先完整读取，再检查编码大小。这是同一内存防护边界需要覆盖的路径。

## 目标与边界

- 在读取完整文件和调用解码器之前，决定是否允许走 Web Audio 全量解码。
- 长音轨、信息不足或预算不够时走现有 HTMLAudio 回退；不破坏普通音频的无缝播放。
- 限制执行中的解码数量，计入 current、next 和预留预算；过期结果不安装到播放器。
- 保持现有音量、暂停、跳转、结束与后端切换语义，不重写播放控制器，不添加新的解码依赖。
- 预算是保守准入，不是操作系统级内存硬上限；不能承诺阻止所有损坏文件或底层解码器引起的 OOM。

## 建议实现

### 1. 提供解码前探测信息

现有 `TrackListItem` 有 duration，但没有完整声道和采样率信息。不能假定这些字段已存在，也不能默认所有文件均为双声道。
优先沿现有播放资源解析链路，在 Main 侧做有界的格式元数据探测，返回文件指纹、时长、声道数、采样率、编码字节数；Renderer 经类型化 Preload/IPC 获取。不要为了探测读取封面或整份 PCM。

先评估已有 metadata 解析能力能否限制为头部读取。无法低成本可靠探测的格式直接回退；不要以无限扫描换取准入结果。按路径及 size/mtime 缓存探测结果，限制缓存条目数，文件变化后失效。无必要不增加数据库字段或全库迁移。

### 2. 预算准入

实现可独立测试的预算函数：验证时长、声道数、采样率均有限且大于零；按 AudioContext 的输出采样率估算 PCM，必要时使用源与输出采样率的较大值作保守估计。

`预计 PCM 字节 = ceil(时长 × 预算采样率) × 声道数 × 4`。

预算必须包含已持有的 current、next、正在解码的预留量、编码输入与合理安全余量；共享同一 buffer 的引用只计一次。安全余量和允许上限集中为常量，在实施时依据测量说明选择，不能把当前 512 MiB 宣称为进程 RSS 限制。
超过限制、信息未知、数值异常或探测已失效时，在 fetch/decode 前返回明确回退原因。仍保留解码后的实际大小检查，应对估计偏差。

### 3. 限制读取与解码生命周期

有 Content-Length 时提前拒绝超限数据；没有或不可信时分块累计读取，一旦超过上限就取消 reader。不能只在完整 arrayBuffer 分配后拒绝。

同一引擎最多一个执行中的 `decodeAudioData`。新请求使旧 generation 过期，但旧解码未完成前仍占用预留预算。前台播放可立即回退 HTMLAudio；预加载可跳过，避免等待旧解码阻塞播放。
预算释放放在 finally，覆盖 fetch 失败、解码失败、取消和过期结果。dispose/cancel 后，旧解码即使完成也不能设置 next、启动播放或重建已销毁的上下文。

### 4. 接入所有路径

首曲 start 与 scheduleNext 共用准入机制。探测、准入失败必须使用现有 runtime 回退，不把本可播放的文件变成致命错误。预加载失败不打断当前曲目，边界到达时由现有切歌逻辑正常播放下一首。
日志记录原因、估计大小、实际大小、预留量与活跃解码数，避免高频 timeupdate 日志。

## 实施与验收

先实现预算函数和单解码状态管理，再补探测契约与调用接线，最后验证回退。按实际读取的模块遵循架构、Renderer 和 IPC 规则。

| 场景                             | 验收结果                                     |
| -------------------------------- | -------------------------------------------- |
| 超长、多声道、高采样率、未知信息 | 准入拒绝时 decodeAudioData 调用次数为零      |
| 普通短音轨                       | 仍可解码，并保留下一首调度能力               |
| current、next 与新请求共存       | 预算包含实际持有及预留量，无重复记账         |
| A 解码未完成时切 B、再 cancel    | 最大执行中解码数为一；A 不安装，预算最终释放 |
| 无 Content-Length 的超限流       | 读取达到上限后中止，不继续收集整文件         |
| 探测、读取、解码失败             | start 正常回退，预加载失败不停止当前歌曲     |

Mock AudioContext 的测试证明调用和生命周期，不证明真实内存峰值。复用 runtime 定向测试并增加必要引擎测试；公共契约变更后执行类型检查。
使用隔离音频样本人工验证一次正常无缝边界及一次超限回退，记录 Renderer 内存和响应情况；不要生成足以使机器失去响应的极端样本。未进行真实音频验证时明确注明。
