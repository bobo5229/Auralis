# 元数据体系优化技术方案

日期：2026-10-28

状态：S1–S5 已实施并完成元数据范围独立验收（2026-10-28）
审计基线：`29d4f4e3`；审计时工作区的未提交源码修改集中在启动专辑动画，与本方案目标模块无关。

## 1. 目标与实施范围

统一文件标签、数据库缓存、历史用户覆盖和展示回退之间的关系，使导入、扫描、文件监听、手动刷新和编辑读回产生一致结果。优先修复日期、M4A 标签别名、清空语义和封面更新问题，再调整编辑契约与持久化模型。

目标行为：新编辑以成功写回并校验后的文件标签为权威；历史 `user_edit` 在完成文件核对前继续保留；展示回退只用于展示。2026-10-28 用户要求接手 S2 并继续剩余阶段，实施状态见文末。真实曲库的批量修复仍需独立限定目标，本轮验证使用隔离数据。

范围覆盖普通文本标签、日期、多值字段、曲目内嵌封面与专辑封面回退。歌词沿用独立编辑链路，继续保留内嵌 TTML 保护、歌词原文校验与 sidecar 指纹机制；仅在公共提交或读取边界变化时补充回归。

现有多值分隔规则沿用[多值元数据统一处理规则](TECHDOC-multivalue-metadata-2026-10-03.md)。本轮数据权威关系已按实施记录同步到该文档及曲库规则；历史覆盖继续受显式来源与覆盖位保护。

## 3. 数据权威与目标模型

### 3.1 四类数据职责

| 数据           | 职责                                               | 更新条件                             |
| -------------- | -------------------------------------------------- | ------------------------------------ |
| 文件标签规范值 | 当前文件的语义快照，保留缺失状态                   | 稳定读取成功并通过最终文件指纹检查   |
| 历史用户覆盖   | 保存升级前无法确认来源的用户值                     | 只有明确核对成功或用户选择后才能解除 |
| 展示派生值     | 文件名、Unknown 文案、专辑艺术家回退、格式化文本   | 从有效标签派生，不参与文件写入       |
| 操作状态       | 编辑版本、写入租约、文件已提交但数据库待恢复等状态 | 由现有编辑协调器维护                 |

普通文件字段的缺失使用 `null`；多值字段在领域层使用数组。数据库与现有列表 IPC 在过渡期继续使用 `; ` 字符串，不改变斜杠、逗号、`&` 和单独分号的现有语义。

`tracks` 逐步收敛为文件规范值及技术字段的持久化来源。`track_metadata` 暂保留兼容缓存及历史覆盖，普通行由同一仓库事务同步。展示视图仅对明确的历史覆盖应用覆盖值，其余字段从文件规范值投影。移除重复缓存列作为后续独立清理，不与首轮迁移合并。

文件名回退由主进程从路径派生，存入独立的 `title_fallback` 列供现有 SQL 展示视图使用；Unknown 文案和多值排版由展示层处理。列表、专辑分组、搜索、排序、播放队列与统计沿用一致的有效展示投影；编辑快照单独读取真实标签，不从已格式化的列表 DTO 反推。切换时保持完整曲库快照与分页游标契约，检查列表映射和压缩传输结构的全部消费方。

### 3.2 新编辑的规则

1. 编辑器加载真实标签规范值；缺失字段显示为空，回退值可作为提示。
2. 请求只携带修改字段；未出现字段表示保持，显式 `null` 或规范化后空列表表示删除标签。
3. 主进程基于最新稳定文件快照合并修改，生成写入意图。写入器保留所有未编辑字段及私有标签。
4. 文件写入、保留校验、发布和最终读回成功后，数据库提交文件读回结果；操作来源可记为用户编辑，但不据此建立永久覆盖。
5. 以后在外部编辑器修改标签时，扫描、监听与手动刷新均更新普通记录。

现有 `commitVerifiedUserEdit` 在契约切换时改为提交验证后的文件快照，取消先将请求整组写成永久覆盖的步骤。扫描与刷新复用同一有效值/历史覆盖合并函数；文件解析不放进数据库事务，仓库只接收稳定快照与期望版本。

已成功写回文件的修改不会因取消数据库覆盖而丢失。若以后需要“只改曲库、不改文件”，应作为具有独立契约的覆盖能力设计。

### 3.3 历史 `user_edit` 的保留

历史整行覆盖没有字段级编辑历史，不能可靠推断哪些字段曾被修改。迁移阶段保留完整的当前有效快照，并将其标为 `legacy_user_edit`。

拟为 `track_metadata` 增加 `override_mask INTEGER NOT NULL DEFAULT 0`，位定义由共享常量集中维护，对应当前七个可编辑字段：标题、艺术家、专辑、专辑艺术家、流派、年份和发行日期。只有历史覆盖使用该掩码；普通文件行掩码为零。

迁移前先完成一致备份。事务内读取旧视图的当前有效值，再将历史行物化为该快照并设置七个覆盖位；原始行可由迁移备份恢复。新视图按覆盖位使用 `CASE` 取值，覆盖位存在时允许返回 `null`，从而消除 `COALESCE` 将“明确空值”解释为继承的问题。新读取器、视图和所有写入分支在同一应用版本切换，避免混用两套来源含义。

后续稳定读取仍更新文件规范值，但保留历史覆盖。完整重扫、自动监听、手动刷新及解析器回填都使用这一规则。文件缺失、不可读、解析失败或值有差异时，覆盖保持有效并记录核对状态。

解除历史覆盖采用以下流程：

- 文件规范值与历史覆盖完整等价时，可在事务中解除覆盖并同步普通缓存；比较使用标签语义，不将 Unknown、文件名或推断的专辑艺术家当作真实标签。
- 存在差异时，向用户提供字段差异及“采用文件值”或“将保留值写入文件”的选择。前者只调整数据库，后者走完整文件写回链路。
- 保留值写回时，使用针对当前真实文件快照生成的修改集；全部覆盖处理成功后才解除整行历史状态。

旧值已被写成 Unknown 等真实标签时，无法仅凭文本判断用户意图；方案不将该类字符串批量清空。

S2 到 S3 的兼容期内，旧版整组编辑入口仍使用历史覆盖策略，但必须同步设置来源与覆盖位，保持所有查询的解释一致；S3 切换后停止创建新的历史覆盖。旧入口不能继续写出缺少覆盖位的 `user_edit` 行。

## 4. 日期与格式适配

### 4.1 日期规则

领域日期采用经过日历校验的 `YYYY`、`YYYY-MM`、`YYYY-MM-DD` 或 `null`，由文本长度表达精度。日期类型、校验和年份派生放入共享纯模块，主进程读取、请求校验、写入和 Renderer 表单共同使用。

新契约以 `releaseDate` 为唯一可编辑日期字段；`year` 作为兼容派生字段，满足 `year = releaseDate 的前四位`。清空日期同时清空派生年份。历史覆盖中的年份与日期冲突在核对前保留，不强行按其中一项覆盖另一项。

公共文件读取按以下顺序处理：

1. 优先解析有效的公共日期；公共年份只有在日期缺失时作为年精度输入。
2. 对 ID3v2.3，补充完整日期形式的 `TYER`，以及标准四位 `TYER + TDAT(DDMM)`，并执行日历校验。
3. 保留原生帧供保留校验和诊断；无效日期不阻断其他字段导入，记录字段警告。
4. `verifyWrittenMetadata` 比较同一日期解析结果，移除独立的 `TDAT` 拼接规则。
5. 普通解析与 M4A 文本快速读取使用相同日期规范。公共规则变更提升解析器公共版本，格式兼容变更提升对应格式版本。

文件写入能力按日期精度验证。尤其对 ID3v2.3 的月精度日期，须用实际写入器证明往返保真；无法表达时返回明确的“不支持该日期精度”，保留原文件。跨标签版本转换作为单独变更评估，不能靠截断日期绕过验证。

### 4.2 M4A 艺术家别名

保持现有明确复数字段的读取优先级。修改艺术家时更新 `©ART`，并同步已经存在的受支持 `ARTISTS` 自由标签；专辑艺术家对 `aART / ALBUMARTISTS` 执行相同规则。数据项与原始大小写变体按已支持命名空间归一识别。

优先采用“同步已有复数字段”的兼容策略，避免对普通文件额外制造别名。每个多值项写为独立 data 项，沿用现有原子文本清洗规则。未修改艺术家时保留相关标签原样。

标签保留校验的排除范围由实际修改字段决定：编辑艺术家时允许其受支持别名变化，编辑其他字段时继续保护这些标签；其他命名空间的私有同名标签保持受保护。最终验证使用完整原生读取结果，确认解析优先级下返回的就是请求值。

### 4.3 字段规则的组织

先提取日期与艺术家别名等已经重复的规则，采用显式类型和纯函数组合。建议形成以下职责边界：

| 位置                              | 责任                                                   |
| --------------------------------- | ------------------------------------------------------ |
| `src/shared` 的元数据类型与纯规则 | 字段类型、日期校验、多值规范化、修改集语义、历史覆盖位 |
| `src/main/features/metadata`      | 格式解码、格式写入能力、保留校验与写后验证             |
| 主进程 repositories               | 文件快照、历史覆盖和索引的事务提交                     |
| `metadataTagWriteCoordinator`     | 写入租约、并发检查、播放协调与失败恢复                 |
| Renderer 编辑组合逻辑             | 表单状态、修改集、冲突提示和保存反馈                   |

格式映射可使用小型静态表，但文件 I/O、数据库 SQL 和页面状态继续由各自模块负责。每次提取都应有现有调用方与回归用例。

## 5. 编辑契约与并发控制

目标契约如下，具体命名在实施时与现有 IPC 类型保持一致：

```ts
interface TrackTagValues {
  title: string | null
  artists: string[]
  albumTitle: string | null
  albumArtists: string[]
  genres: string[]
  releaseDate: string | null
}

interface TrackMetadataEditSnapshot {
  trackId: number
  editToken: string
  values: TrackTagValues
  // 历史覆盖值及其与文件值的差异另用显式结构返回。
}

interface UpdateTrackMetadataRequest {
  trackId: number
  editToken: string
  changes: Partial<TrackTagValues>
}
```

`changes` 缺失属性表示保持，标量 `null` 和多值空数组表示清空。运行时校验拒绝未知键、无效 ID、超长文本与超量列表；规范化后空修改集直接返回成功。若传输需要保留旧字符串形式，使用边界适配器转换为领域数组。

`editToken` 由主进程生成并校验，绑定 track ID、当前路径身份、文件指纹和该曲目的元数据/历史覆盖修订。采用不透明 token，Renderer 不自行构造，也不以整个曲库的 revision 代替单曲编辑版本。主进程维护有界 token 状态，失效后要求重新加载。

首次打开编辑器时稳定读取当前文件文本标签，可跳过封面与时长计算，再生成快照与 token。迁移前留下的文件名、Unknown 或旧规范化缓存不能直接作为“真实标签”返回。文件不可读时普通编辑返回明确失败；历史保留值仍可查看和比较，但写回须等文件可读后执行。

保存顺序：验证请求 → 获取现有写入租约或播放编辑能力 → 核对 token 并稳定读文件 → 合并修改集 → 准备暂存文件并核对文件未变 → 校验目标字段和未修改标签 → 发布 → 稳定读回 → 事务提交 → 发布现有曲库 revision 事件。提交前再检查曲目路径、编辑版本和 generation，防止过期读回覆盖新状态。

打开编辑器后文件或有效元数据发生变化时，返回专门的 `metadata-conflict`，保留表单修改并提示重新加载、比较差异。现有 `file-changed` 继续表示准备或发布过程中发现源文件变化。

IPC 修改同时更新 `contracts.ts`、运行时 payload 校验、显式 Preload API、处理器和 Renderer 消费方。Renderer 继续通过类型化 IPC 访问能力。现有播放写入租约、buffered playback、关闭 drain、watch 抑制及旧结果丢弃机制随新契约保留。

### 文件已发布后的恢复

文件发布和 SQLite 事务之间存在跨资源失败窗口。数据库失败时，沿用现有待核对状态，由协调器重读文件、验证意图后补交；补交不得再次写文件。再次保存必须区分“尚未发布”和“文件已发布、等待数据库恢复”。

重启后，由稳定文件指纹比对和扫描/监听恢复普通文件缓存。历史覆盖记录需要更严格处理：若文件已改变而数据库仍保留旧覆盖，只能核对并报告差异，不能自动将旧值再次写回。若后续要求重启后自动识别每一笔未完成写入，再单独引入持久化操作记录；本轮先验证现有恢复路径能收敛普通记录并保留历史数据。

## 6. 封面来源与引用更新

封面缓存 key 标识内容及转换配置；v2 只说明缓存格式有效，不能证明来源内容未变化。

### 6.1 曲目内嵌封面

为 `tracks` 规划独立的 `embedded_artwork_cache_key` 和 `embedded_artwork_checked_fingerprint`。前者可为空，后者为空表示尚未完成对应文件版本的封面读取。读取结果显式区分四种情况：

| 结果                   | 数据库动作                                         |
| ---------------------- | -------------------------------------------------- |
| 已读取且存在封面       | 更新 key 与已核对文件指纹，允许 v2 A 更新为 v2 B   |
| 已读取且没有封面       | 清空内嵌 key，记录已核对文件指纹                   |
| 文本快速路径未读取封面 | 保持已有封面状态，不将其解释为删除                 |
| 解析或转换失败         | 保留已有可用引用并记录失败，不标记本次封面读取成功 |

文件指纹变化时重新读取封面；未变文件的文本回填继续跳过封面字节，保留现有增量扫描收益。

### 6.2 专辑回退与缓存回收

当前目标顺序为“本曲目的有效内嵌封面 → 同专辑的可用代表封面 → 空态”。历史编辑行中由专辑复制来的封面 key 不能自动认定为用户指定封面；核对来源前保留为兼容回退。

同一专辑的代表封面按固定顺序选取，例如 disc、trackNo、track ID，空序号的排序规则显式固定。曲目封面、专辑归属、可用性变化时，仅重算受影响的旧/新专辑，避免扫描顺序决定最终封面。整张专辑没有有效内嵌封面时，清理失效的自动代表引用，同时保留仍未核对的历史兼容来源。

对应文件版本的内嵌封面读取一旦成功，就停止使用该曲目的旧兼容 key；“确认不存在”同样可以结束旧 key 的回退。来源尚未核对或转换失败时继续保留兼容引用，避免迁移期间空白封面被误判为最终状态。

引用更新与曲目/专辑数据在同一事务提交，再沿用现有曲库变更通知。缓存引用查询、引用索引和 GC 必须纳入新增列及历史兼容引用；新缓存文件生成成功也不立即删除旧文件，回收以实际引用为准。

## 7. 数据迁移与回填

所有结构变更由 `schemaMigrations.ts` 定义并经现有 `schema.ts` 执行，迁移编号在实施时按当前最后版本追加。结构迁移只处理数据库，音乐文件解析安排到可中断的后台回填。

1. **迁移前备份**：复用现有一致备份机制，保留 WAL 中已提交数据；先用隔离数据库验证升级和恢复。
2. **增量结构迁移**：添加历史覆盖位和封面来源字段，物化历史覆盖当前有效快照；普通记录保留为待核对文件缓存。
3. **后台回填**：结合解析器版本、文件指纹及封面核对状态，分页重读真实文件。普通记录更新真实缺失值；历史覆盖只更新底层文件值并记录差异。
4. **提交边界**：沿用路径、文件指纹、generation、sidecar 指纹和当前 root 范围检查；读取失败保持旧数据与未完成标记，下一轮可重试。
5. **幂等与进度**：使用已完成的逐记录版本/指纹判断跳过，游标只控制遍历顺序；失败项保持可重新选取，重启可继续，用户主动操作保持优先级。
6. **索引同步**：`track_artists` 从最终有效艺术家列表生成，确保扫描、刷新和历史覆盖解除都更新同一投影；普通文件快照与有效列表不同时，关联表明确服务于有效曲库视图。
7. **兼容退出**：完成主要消费者切换并验证后，再评估清理 `track_metadata` 普通缓存列及未使用索引。清理工作使用单独迁移与验收。

存量回填只更新数据库与派生缓存。文件写入仅来自明确的用户编辑或历史覆盖处理选择。回滚使用匹配升级前版本的数据库备份；数据库恢复不会撤销已完成的音乐文件写回，恢复后需重新扫描文件。
