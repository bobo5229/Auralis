# 歌曲改名与移动后的路径找回

日期：2026-10-04。范围：文件改名或在当前曲库目录内移动，找到唯一匹配时保留原记录身份。状态：实现及自测完成。

## 目标行为

用户在播放器外改名或移动音乐文件后，Auralis 更新原歌曲记录的文件路径。原歌曲 ID、创建时间、歌单位置、播放次数、逐日播放记录和已有展示元数据继续保留。文件标签由 fb2k 等外部工具维护；Auralis 在本流程中只读取音乐文件。

例：`old.flac` 改为 `new.flac`，原歌曲 ID 为 9，已有 7 次播放并在收藏歌单中。处理后仍是 ID 9、7 次播放及原歌单位置，播放入口按 ID 读取新路径，不新增另一条同曲记录。

本次实施只覆盖路径找回。目的路径已经入库的历史重复记录合并、确认缺失后的删除、流派上层分类及播放历史存储改造属于后续独立范围。移动到配置曲库之外的文件需要重新纳入扫描范围；本次全量扫描只对本轮完整枚举的当前曲库目录作缺失与找回判断。

后续“确认删除文件”已另行实现，保留收听历史，见[曲库清理交付](TECHDOC-deleted-track-cleanup-2026-10-04.md)；该变更已独立复验通过，并完成真实数据库清理。

## 发现的现状问题

- 全量扫描原先边读边插入新路径，到扫描结束才标记旧路径缺失。应用关闭期间发生改名后，第一次重扫可能先插入新 ID，再把旧 ID 标为缺失。
- 文件监听先处理存在的新路径，随后延迟确认旧路径缺失。新路径事件先到达时，原记录仍为 `available`，只查询 `missing` 的匹配器无法找回它。
- 监听另有一套只考虑最近缺失记录的解析和匹配流程，跳过增量导入的稳定性检查，形成两条不同的处理路径。
- 逐条匹配后立即修改候选，会使两个新路径竞争一个旧 ID 时由处理顺序决定谁接管记录。

## 统一匹配规则

沿用已有身份判定，并在写入前完成整个待处理集合的匹配。

1. 同一 ISRC 只有一个旧候选，双方时长均为有限正数且相差不超过 1 秒，才允许匹配。ISRC 有歧义或时长冲突时停止匹配。
2. 没有命中 ISRC 时，使用无 ISRC 的旧候选：标题与艺术家一致、时长相差不超过 1 秒、大小相差不超过 2%，专辑相同或至少一侧没有有效专辑名。
3. 一个新路径只能有一个旧候选；同一个旧 ID 也只能被一个新路径认领。竞争时保留旧记录，将新文件按正常导入处理。
4. 旧文件仍存在时，新文件作为独立副本导入。Windows 中仅大小写或路径分隔符变化属于同一路径，可保留身份并更新路径拼写。访问权限或其他 I/O 错误不能证明旧文件消失，不自动迁移该候选。
5. 更新时核对旧 ID 仍指向预期旧路径；目的路径被另一条记录占用时拒绝接管，保持旧记录及其关联数据。本次不合并目的路径已有记录。

这是保守的元数据匹配，没有新增音频内容哈希。不同文件同时改标签、缺少时长、匹配歧义或不满足阈值时，继续作为新文件导入，旧记录维持缺失状态。

## 全量扫描流程

1. 保持已有目录枚举、标签读取及已知路径更新流程。新路径读取结果暂存于本轮扫描的内存集合，按路径去重。
2. 只有收到有效的扫描完成消息后，才在数据库事务内恢复已发现路径并标记本轮未发现的旧路径。
3. 候选限定于当前扫描目录，排除未能读取的目录。用完整新路径集合与候选集合统一匹配。
4. 唯一匹配更新原记录；未匹配的新文件正常插入。扫描完成状态、缺失标记和路径找回在同一事务中提交。
5. 提交后发送既有 `track-relocated`、`track-added`、`track-restored`、`track-missing` 事件。已在本轮找回的 ID 不再发送 `track-missing`，避免界面先把同一歌曲从队列移除。
6. 扫描失败、取消或关闭时丢弃未提交的新路径集合，下一轮重新读取；已知路径的正常更新仍沿用原扫描行为。

新路径会在完整扫描结束后进入曲库；暂存内存随本轮新文件数量及歌词数据增长。初次大批导入期间可见的扫描进度继续更新。

## 文件监听与增量导入流程

1. 监听的新路径统一进入现有增量导入器。并行等待每批最多 32 个文件稳定，串行解析标签、封面及歌词。
2. 整轮解析成功的结果收集后统一匹配，避免跨批次的两个路径认领同一个旧 ID。
3. 从数据库按身份查询候选，包含 `available` 与 `missing`；逐个检查候选旧路径。仅 `ENOENT` 或 `ENOTDIR` 才作为已不存在的证据；仅大小写变化的同一路径按 Windows 路径语义识别。
4. 对确认缺失且唯一匹配的候选更新原记录，再发送路径找回事件。读取失败的文件单独报告；未匹配文件仍按原有批次导入。
5. 旧路径的后续监听确认按当前数据库路径查找，不会把已迁移到新路径的 ID 标为缺失。保留既有短暂缺失确认和导入重试机制，处理文件替换过程。

移除监听内部的最近候选缓存、到期计时器和重复标签解析；目录监听只负责事件分发、缺失确认及重试，匹配规则集中在共享匹配器。

## 数据与实现范围

- `trackRelocationMatcher.ts`：保留已有匹配阈值，增加整批双向唯一性判断。
- `libraryScanService.ts`：暂存新路径，完成扫描时在事务中找回，提交后发布事件。
- `libraryIncrementalImportService.ts`：完整导入集合统一匹配，并检查旧路径实际不存在。
- `metadataWatchService.ts`：统一使用增量导入，保留导入期间事件去重及关闭等待。
- `trackRepository.ts`：候选查询支持尚未标记缺失的记录；路径更新核对预期旧路径，并保存本次读取到的歌词旁文件指纹。

不变更数据库结构、IPC 契约或文件写回策略。通过原 ID 保留所有按 ID 关联的数据，已有 `track_metadata` 保持原样；基础标签与文件指纹随本次读取更新。

验证使用隔离临时文件和 Electron 原生内存数据库，不操作真实音乐收藏或真实数据库。

- 原生服务验证：首次重扫旧记录仍为可用、同 ISRC 的不同长度版本、未读目录、复制文件、跨 worker 消息竞争、失败与取消、事务提交失败回滚及事件发布时机。
