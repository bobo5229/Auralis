# GPT-6.1 Sol 任务与推理档位参考

适用于使用 GPT-6.1 Sol 开发、维护和审查 Auralis。日常从 **Medium** 开始；明确的机械修改用 **Low**；多模块状态联动用 **High**；疑难归因和重要机制设计用 **Extra High**；少数深入推演用 **Max**；适合并行拆分的大任务再考虑 **Ultra**。

以下任务档位是 Auralis 的项目建议，尚未经同题对照测试；按当前任务从推荐起始档位判断并逐步调整。本文供选档参考，执行中的授权、子代理派遣和验收遵循项目现行规则。

官方资料核对日期：2026-10-25。模型、客户端或档位机制变化后，应重新核对官方说明。

## 快速选档

| 档位 | 主要判断 | 使用方式 |
| --- | --- | --- |
| Low / Light | 改什么、怎么改都明确，影响局部 | 执行确定的修改、提取事实、运行既定检查 |
| Medium | 目标明确，需要理解局部代码和少量设计 | 日常功能、局部修复、普通文档与方案初稿 |
| High | 多个模块、状态或生命周期相互影响 | 跨层实现、异步状态追踪、共享逻辑调整 |
| Extra High / `xhigh` | 根因不明、证据冲突、方案取舍复杂 | 复杂故障归因、重要机制设计、整体视觉系统设计 |
| Max | 单个核心问题需要非常深入的探索与核对 | 难题推演；质量收益值得额外时间和用量时使用 |
| Ultra | 工作能拆成有意义的独立部分，并行有明确收益 | 多方向调查或大范围独立审查，仍遵守当前派遣授权 |

文件数、代码行数、命令耗时和日志长度主要影响工作量，不能单独决定推理档位。长时间运行构建通常不需要高档位；一个涉及并发的短函数可能需要 Extra High。

## 典型任务映射

### 文档、界面与交互

| 典型任务与前提 | 推荐起始档位 | 何时升档 |
| --- | --- | --- |
| 修改确定的文案、翻译键、注释或文档链接 | Low | 文案背后涉及产品行为或多处语义一致性，升 Medium |
| 按明确设计值调整字号、颜色、间距、圆角 | Low | 需要决定布局、处理缩放或多个窗口尺寸，升 Medium |
| 解释一个函数、查某个配置或调用入口 | Low | 需要追踪跨进程事件和完整生命周期，升 High |
| 整理已有结论，编写参考文档或交接说明 | Medium | 需要解决证据冲突或设计复杂实施顺序，升 High 或 Extra High |
| 修复可稳定复现的局部菜单、焦点或文字裁切问题 | Medium | 涉及共享浮层、事件优先级和多组件联动，升 High |
| 按现有模式增加仅影响 Renderer 的显示设置 | Medium | 设置影响主进程行为、持久化和启动恢复，升 High |
| 已有明确设计稿，完成一个页面的布局与交互 | Medium | 牵涉共享组件、路由状态或复杂转场，升 High |
| 调整共享菜单、列表行或全局主题变量 | High | 不同页面存在冲突约束，需要重定语义体系，升 Extra High |
| 统一曲库、唱片室、全屏聆听的视觉与交互体系 | Extra High | 整体方案确定后，局部落地降到 Medium 或 High |
| 调整已有 Canvas / GLSL 效果的明确参数 | Medium | 需要设计材质算法、处理坐标与渲染阶段耦合，升 High；复杂视觉与性能取舍用 Extra High |

### 播放、曲库、数据与进程边界

| 典型任务与前提 | 推荐起始档位 | 何时升档 |
| --- | --- | --- |
| 按已有安全模式增加普通 Renderer → Preload → Main 调用 | High | 改变信任边界、路径权限或调用身份校验，升 Extra High |
| 实现播放队列操作并同步当前曲目、封面和进度 | High | 快速切歌、跳转、加载完成事件存在竞态，升 Extra High |
| 修改曲库筛选、排序、分页与列表状态联动 | High | 查询快照、并发请求和库变更导致一致性问题，升 Extra High |
| 修改扫描进度、取消、失败反馈与重试交互 | High | 涉及提交原子性、退出中断或增量扫描指纹一致性，升 Extra High |
| 复用现有格式化函数统一多页面元数据显示、缺省值与格式 | Medium | 多入口语义冲突或缓存、跨层一致性问题，升 High；存量数据解释、规范化或写回语义复杂变化，升 Extra High |
| 修改窗口关闭、订阅注销、定时器与资源释放 | High | 多窗口、退出流程和播放资源相互等待，升 Extra High |
| 设计数据库迁移、音乐文件写回或删除后的恢复策略 | Extra High | 中断、恢复与一致性组合十分复杂且需要深入推演时，用 Max |
| 重构播放状态模型或跨模块资源所有权 | Extra High | 方案与边界确定后，按实施难度降到 High |

### 诊断、性能、审查与验证

| 典型任务与前提 | 推荐起始档位 | 何时升档 |
| --- | --- | --- |
| 运行已选定的检查命令、摘录失败信息 | Low | 分析简单失败用 Medium；涉及原生依赖、ABI 或进程环境关联用 High |
| 为局部明确行为补充有价值的回归测试 | Medium | 需要构造并发、取消、失效回调或跨层事件路径，升 High |
| 修复根因已经确认、方案明确的局部缺陷 | Medium | 修复影响共享行为、数据契约或异步状态，升 High |
| 审查局部功能差异与需求覆盖 | Medium | 必须追踪多个调用方、状态源或外部副作用，升 High |
| 审查 IPC 权限、数据完整性或复杂播放并发 | Extra High | 极复杂的不变量与恢复路径需要更深入核对时，用 Max |
| 有性能记录，瓶颈已定位，实施局部优化 | High | 存在多个相互影响的瓶颈或优化会改变行为，升 Extra High |
| 大曲库滚动、扫描或进入页面偶发卡顿，原因未知 | Extra High | 先测量并缩小范围；单纯缺少数据不构成升 Max 的理由 |
| 调查快速切歌、拖动进度与异步加载交叠时的偶发错乱 | Extra High | 已有事件证据仍难解释、需深入比较多个假设时，用 Max |
| 全面审查多个可独立分析的子系统 | Ultra，前提是允许且值得并行 | 各子任务分别选档；若强依赖同一条事件链，考虑单代理 Extra High 或 Max |

## 升档与降档条件

先按任务表选择起点。出现以下情况时，重新判断档位，而不是机械地连续重试：

- **Medium → High：**局部问题实际跨越多个状态源、共享调用方或进程；修复需要协调取消、失效与释放顺序。
- **High → Extra High：**出现多个合理但互斥的解释；现有证据互相矛盾；需要比较行为、性能、兼容性之间的重要取舍。
- **Extra High → Max：**关键证据已具备，困难集中在深入推演、假设比较或完整性核对，额外推理有明确用途。无需为了使用 Max 先制造一次低档失败。
- **转向 Ultra：**能明确列出相对独立的子任务、各自交付物和汇总方式，并行收益超过重复读取与协调成本。Ultra 不是 Max 失败后的必经下一档。
- **降档：**根因或方案已经确定，剩余工作是局部实施、重复应用既有模式、整理结果或执行明确检查。

缺少复现步骤、日志、设计目标或验收标准时，先补齐影响判断的信息。安装失败、访问受限、工具报错也应先按具体证据处理，不能直接归因于推理档位太低。

选择档位与选择验收强度分别进行。高风险任务即使用 Max，也仍需按[风险与验收](../rules/validation.md)完成必要检查和独立验收；界面与性能结论仍需要相应运行证据。派遣按[子代理派遣与额度](../rules/agent-dispatch.md)及当前授权执行。

## 同一任务可以分阶段选档

| 任务 | 方案或诊断阶段 | 实施阶段 | 收尾阶段 |
| --- | --- | --- | --- |
| 增加普通显示设置 | Medium | Medium | 明确的文案与结果整理用 Low |
| 重构播放队列状态管理 | Extra High | High | 验证中需要分析的并发问题继续用 High 或 Extra High |
| 统一多页面视觉体系 | Extra High | Medium / High | 已定参数的局部调整用 Low / Medium |
| 处理扫描中断与提交一致性 | Extra High，必要时 Max | High / Extra High | 独立验收按剩余判断难度选档 |

降档后仍保留既定边界、有效证据和验收要求。文档中的档位建议不会自动切换当前会话配置；实际使用所选客户端支持的控制项。

## 如何逐步找到适合我们的档位

从日常任务中选少量有代表性的案例，比较同档和低一档的结果。不要在真实音乐文件或数据库上重复执行有副作用的任务；需要对照时使用隔离副本或只读材料。

| 记录项 | 观察内容 |
| --- | --- |
| 任务与档位 | 任务范围、已知证据、所选模型与档位 |
| 质量 | 是否满足需求、遗漏了哪些关键边界、相关验证是否通过 |
| 返工 | 是否需要人工纠正、回退方案或多轮修复 |
| 总开销 | 完成整个任务的时间与用量，包含子代理和返工 |

保留能稳定达标的最低档位。低档的一次成功或高档的一次失败，都不足以确定长期选择。官方也建议使用相同输入进行比较，选择满足质量要求的最低设置。[官方模型选择建议](https://developers.openai.com/api/docs/guides/model-selection#experiment)

拿不准时，可以先发出一个只读判断请求：

> 请根据 GPT-6.1 Sol 任务与推理档位参考，结合这次任务和必要的只读检查，推荐一个起始档位，说明一句理由和一个升档条件；暂不实施。

## 官方档位与 Ultra 说明

- GPT-6.1 Sol 的 API 支持 `low`、`medium`、`high`、`xhigh`、`max`，默认 `medium`，不支持 `none` 和 `minimal`。客户端默认值与 API 默认值应分别判断。[官方模型指南](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-6.1-sol)
- Light 对应面向用户的轻量档位名称，CLI 使用 Low；Medium 平衡速度与深度；High 和 Extra High 面向多步骤、多来源或复杂取舍。Max 给单个任务更多推理时间，多数任务不需要 Max 或 Ultra。[官方档位说明](https://learn.chatgpt.com/docs/models#pick-a-reasoning-effort)
- 官方对 GPT-6.1 Sol 的例子包括：Medium 用于需要迭代的复杂技术工作，Extra High 用于精细交付、相互关联的视觉系统和冲突证据下的决策。本文将这些方向映射到 Auralis，具体任务分档属于项目建议。[官方模型选择指南](https://developers.openai.com/api/docs/guides/model-selection)
- 官方将 ChatGPT Work 的 Ultra 描述为最高强度推理与主动子代理委派的组合。Codex 本地客户端的委派仍受明确请求和适用项目规则约束；可用选项取决于客户端、账户和模型。不要把 Ultra 直接当作该模型 API 中列出的 `reasoning.effort` 值。[官方子代理说明](https://learn.chatgpt.com/docs/agent-configuration/subagents#choosing-models-and-reasoning)
- 并行工作可以缩短等待时间，但主代理和子代理各自消耗输入、推理与输出 token，还需要协调和汇总。Ultra 通常预期用量较高，不存在每次都最多或固定倍数的保证。比较时看整个任务的总开销。[官方用量说明](https://developers.openai.com/api/docs/guides/agents-api/observability#model-usage-and-cost)
