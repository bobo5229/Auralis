# 深浅主题切换性能优化复盘

复盘日期：2026-11-06。

用户报告：在专辑列表页，通过侧栏底部工具栏切换全局深浅主题时会卡顿。本次先审计，再实施优化。最值得保留的经验是：共享颜色变量把局部动效带到了全局；优化原型又通过强制样式读取、继承变量写入和颜色字符串改写，制造了新的启动尖峰。换成透明度动画后，仍需检查准备阶段和文字所在的实际表面。

本文区分原实现的问题、优化中引入的问题和测量方法的问题。经验用于相似任务参考，验证要求以[风险与验收](../rules/validation.md)为准。

## 本次证据与结果

验收使用 Electron 38.8.6 / Chromium 140、可见原生窗口、1426 × 837 CSS 像素客户区、DPR 1.5，以及 50 张模拟专辑和测试封面。测量发生在页面加载稳定后，包含两种方向的首次切换和重复切换；没有将应用冷启动混入主题切换数据。

| 指标                           | 原实现对照组 |              最终方案 |
| ------------------------------ | -----------: | --------------------: |
| 最大 rAF 帧间隔                |       33.4ms |                16.7ms |
| 每次切换的样式更新累计耗时均值 |      397.5ms |   133.8ms，下降 66.3% |
| 每次切换的绘制累计耗时均值     |       62.7ms |     9.0ms，下降 85.7% |
| 切换次数                       |         4 次 | 深转浅、浅转深各 4 次 |

帧间隔统计点击后 850ms 的样本；样式和绘制耗时分别累计每轮 trace 中的 `UpdateLayoutTree`、`Paint` 事件，再跨轮取均值。累计耗时不能当作单帧耗时。rAF 帧间隔反映 Renderer 调度节奏，本轮没有直接统计屏幕实际呈现的丢帧数。

最终实现对普通界面的三块大面积表面使用 220ms 背景图层淡化，文字按预先计算的对比度阈值更新。专辑详情取色、浮动歌词和唱片室继续使用各自已有路径；上表对应普通专辑列表布局。

## 1. 共享颜色变量把专辑动效带成了全局动效

全局主题入口 `useTheme` 只更新主题状态、根节点 `data-theme`、`color-scheme` 和本地偏好。它没有显式启动整页转场，但下游样式已经声明了动画：主内容区、侧栏、歌词区及颜色时钟共同使用 `--album-surface-color`，过渡时长为 650ms。

这套变量原本服务于专辑取色。普通页面也把它连接到主题背景 token，切换根主题便触发整组颜色过渡。只读主题按钮或 `setTheme()`，容易得出“这里只改了一个属性，应该很轻”的判断；真正的开销藏在消费者中。

本次还存在另一条容易混淆的入口：唱片室的局部深浅切换使用 `startViewTransition()`，与侧栏底部的全局按钮不是同一路径。用户补充具体页面和按钮后，才把测量集中到正确入口。

后续检查主题动效，沿着“按钮 → 状态提交 → 根属性 → 颜色别名 → 消费表面与过渡声明”追踪。共享 token 的使用范围扩大时，动画的影响范围也要重新核对。

## 2. `steps()`、WAAPI 和少量变量都没有自动带来低开销

本次背景颜色过渡伴随持续绘制工作。配套的前景色同步还在面板上通过 WAAPI 修改继承的 CSS 自定义属性。即使关键帧使用 `steps(1, end)`，这些属性的消费者仍可能参与样式更新。`@property --album-surface-color` 的 `inherits: false` 只约束该属性，不能替其他继承的文字变量减少更新范围。

我们先尝试把部分前景色动画改成阈值定时更新，保留原背景动画。该组最大帧间隔仍为 24.7–45.8ms，没有形成稳定收益。改动了动画 API，却没有消除整条路径上的主要开销。

另一个原型使用整页快照淡化。其样式更新总量明显下降，但首次切换仍出现 41.6ms 的最大帧间隔，后续多次约为 20.9ms。这个结果没有证明快照方案普遍更慢；它证明本次原型仍未满足启动帧预算，不能仅凭动画阶段轻就认定方案达标。

后续选择动画方案，分别测准备、提交和播放阶段。WAAPI 的性能要结合实际属性、继承范围与绘制面积判断。本轮最终也使用 WAAPI，但动画属性换成了独立背景图层的 `opacity`。

## 3. 第一版背景图层方案把读写交错搬进了切换入口

第一版图层原型按表面依次执行：读计算样式、算文字颜色、插入图层、写变量、启动动画，再处理下一个表面。前一个表面的写入使样式失效，后一个表面的读取又要求浏览器立即给出结果。

下面是这一问题的简化结构：

```ts
for (const surface of surfaces) {
  const style = getComputedStyle(surface)
  const plan = prepare(style)
  surface.append(createLayer(plan))
  applyForeground(surface, plan)
}
```

我们原本想减少持续重绘，却在点击处理阶段制造了重复的样式求值。这一版的最大帧间隔达到 33.3–70.8ms，比原实现更差；重绘总量下降掩盖不了启动阶段的回退。

修正分了两步。先把所有新样式读取和计划计算放在写入之前，避免在多个表面之间反复读写；再把背景图层提前准备好，让浏览器自然处理新调色板后，才开始淡化。批量读写后的中间版本仍有 25.0–37.5ms 尖峰，说明只完成第一步还不够。

`nextTick()` 在这里也曾被用错位置。它等待 Vue 完成更新，不表示浏览器已经绘制。若在主题提交后的微任务中立即读取新样式，随后继续写图层和变量，同一帧仍可能承担两轮大范围样式更新。

最终方案在同步 watcher 中承接旧背景和旧文字，提交新主题后，通过嵌套 rAF 分阶段开始淡化。这是针对本次绘制顺序的安排；rAF 次数本身不代表字体、图片或其他异步资源已经准备完成。

## 4. 同一个颜色换了字符串写法，又让近千个元素更新了一次

这是最后一段启动尖峰中最具体、也最容易被自己忽略的问题。

旧文字颜色从计算样式中的自定义属性读取，可能保留十六进制形式；对比度计划输出的是 `rgb()`。第一帧于是做了这样的赋值：

```ts
// 视觉颜色相同，继承变量的字符串值发生了变化。
surface.style.setProperty('--auralis-text', '#f3eee6')
surface.style.setProperty('--auralis-text', 'rgb(243 238 230)')
```

我们以为第一步只是在保持旧文字颜色，浏览器却需要重新求值这批变量的消费者。详细 trace 中，点击后约 30.5ms 开始的一次 `UpdateLayoutTree` 涉及 919 个元素，耗时约 16.0ms。仅这一轮重复更新，就接近整份 16.7ms 帧预算。

最终在持有旧前景色时，就把可解析的不透明颜色统一成与计划相同的 `rgb(r g b)` 格式；后续赋值前比较当前内联值，跳过未变化的写入。修正前保留的一组数据仍有 20.9ms 尖峰，修正后的正式八次测量为 12.4–16.7ms。

复用经验：向高层节点写继承变量前，统一值的表示，并检查是否真的变化。视觉等价和字符串等价是两回事；颜色格式、单位和数值序列化差异，都值得沿消费者范围检查。

## 5. 为整块面板保护文字对比度，误伤了内部独立底色的控件

背景图层渐变时，直接把文字切到新主题，会出现深色旧背景配深色新文字的阶段。因此，原型暂时持有旧文字，再按背景变化计算切换阈值。

问题出在持有范围：文字变量写在主面板上，其后代会一起继承。搜索框有自己的底色，已经立即切成浅色，文字却仍跟随主面板保留旧的浅色文字。端点都正常，过渡截图中搜索内容却看不清。

修正时又曾扩大到侧栏状态卡和快捷键提示。复查发现，这些区域使用透明或混色背景，仍依赖外层面板；把它们的文字强行切到新主题，同样会破坏过渡中的对比度。最终只让确实拥有独立底色的搜索控件读取新主题文字别名。

这次坑在于把 DOM 继承范围当成了视觉背景范围。后续保护文字对比度时，要核对文字背后实际绘制的表面，分别处理面板正文、独立实色控件和透明材质。验证至少包含两个方向的过渡中段，并核对 placeholder、次级文字和图标；静态端点截图覆盖不到这个问题。

## 6. 测量方式几次让我们接近错误结论

### 离屏结果不能替代可见窗口

首轮离屏测量中，歌曲页和专辑页的最大 rAF 帧间隔都约为 16.8ms；切到可见窗口后，原实现连续四次测到 20.9–29.2ms。两组窗口的调度方式和客户区尺寸不同，不能直接互相证明流畅度。

离屏测试适合检查组件、事件和算法路径。用户报告可见桌面窗口卡顿时，页面性能结论需要对应的可见窗口证据。

### 总开销下降后，单帧仍可能更差

快照原型和第一版背景图层都减少了累计工作，却保留或放大了启动尖峰。短时动效要同时看工作总量、单帧耗时，以及尖峰发生在点击后哪个阶段。仅比较平均值，会把集中在第一帧的成本藏起来。

“没有长任务”也不能证明没有掉帧：16.7ms 的帧预算和 50ms 的长任务门槛不同。本轮验收脚本还按 `entry.startTime >= start` 过滤长任务，这会漏掉开始于触发点之前、但与观察窗口重叠的任务。后续应按区间重叠筛选，并对照完整 `RunTask`；这项脚本边界问题尚未在本轮修正。

### 并行检查与开发热重载会污染样本

一次采样与类型检查、测试进程重叠，前两次出现额外尖峰。后续将性能采样单独运行。重叠记录能说明存在干扰条件，不能单独证明某次尖峰就由检查进程造成，也不能据此把失败样本随意剔除。

首次加载时，Vite 的依赖预编译还触发过页面重载：刚读取到应用 ready，页面随后又进入初始化。应等开发服务稳定，再检查当前页面 ready 和目标内容确实就绪；“首次主题切换”和“首次加载开发依赖”分别记录。

## 7. 详细 trace 加得偏晚，增加了试改和复验次数

前期主要依靠帧间隔、长任务计数和累计样式耗时，在快照、定时更新和背景图层之间试验。这些指标能告诉我们哪一版没达标，但不能指出哪次写入触发了整棵子树更新。

详细 trace 加入后，才把 `start()`、前景色 `apply()` 与大范围 `UpdateLayoutTree` 对上，并定位到同色不同字符串的写入。原因未明时，可用相关开关对照缩小到背景、前景或材质，再按现有证据决定是否采详细 trace；已有具体尖峰且需要精确定位时，可直接检查触发点附近的函数调用、元素更新数量、布局、绘制与合成阶段。

本轮多次覆盖同名结果文件，后来才为部分中间版本另存副本。后续遇到有价值的失败时，保留关键错误、运行条件和仍需比较的结果，避免覆盖；多轮对照、难复现问题或需要交接时，再用独立编号或目录整理并索引。性能对照应能对应所比较的代码版本与采样配置。

检查期间还发生了其他会话对 App 和前景色同步模块的修改。用户要求暂停后，本轮暂停 goal、停止测试服务，恢复后核对源码再继续。共享文件在变化时，不能把不同版本的测量当成同一轮连续优化；原有未提交修改也不能被试验性回退覆盖。

## 8. 异步过渡的完成条件必须覆盖退出路径

最终方案新增了临时图层、内联文字覆盖、rAF、定时器和动态效果偏好监听。只等淡化播完，无法覆盖快速再次切换、离开页面、卸载或中途开启“减少动态效果”。

实现用代次标识阻止旧回调继续生效，并集中清理图层、动画、定时器、rAF 和监听，恢复原内联值及优先级。定向测试覆盖这些生命周期与偏好边界；可见窗口另外核对了连续切换后的最终主题、临时层清理、应用内减少动态效果偏好，以及通过媒体偏好模拟的系统减少动态效果设置。

本轮早期测试仍假定 `nextTick()` 后动画已经创建，加入 rAF 分阶段准备后便失败。测试随后显式推进受控帧调度，再检查动画结果。测试等待的阶段应与产品真实执行顺序一致，不能靠放宽断言掩盖尚未执行的回调。

## 后续复用建议

- **界定范围。** 确认页面、按钮和布局模式，沿实际调用路径追踪主题 token 的消费者。只有需要性能结论时，才在稳定的可见窗口中，用固定且可比的窗口尺寸、DPR、内容和采样方式记录首次与重复切换。
- **按证据定位。** 原因已明确时，直接处理已确认的开销并验证当前性能目标；原因未明时，用相关开关对照缩小到背景、前景或材质。已有具体尖峰且需要精确定位时，可直接采详细 trace；现有证据仍无法解释问题时，再扩展 trace 检查。
- **检查受影响路径。** 修改样式更新顺序或继承变量时，批量读取和写入并跳过未变化的值。修改文字同步或过渡视觉时，检查深浅两个方向的过渡中段文字与实际背景。修改临时图层、回调、卸载或动态效果偏好路径时，检查对应退出行为。
- **复用并结束。** 已有证据按受影响范围复用；当前行为和性能目标达成且没有待处理问题时结束，代码、环境、输入或结论变化时再补做对应检查。
