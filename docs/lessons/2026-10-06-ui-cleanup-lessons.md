# UI 冗余清理经验

复盘日期：2026-10-06。

具体删除边界和验证结果见[第一批清理记录](../reviews/2026-10-06-confirmed-redundancy-cleanup.md)与[第二批筛查记录](../reviews/2026-10-06-redundancy-second-pass.md)。

本次清理围绕主界面流光背景、播放栏材质和历史液态玻璃实现展开。最有价值的经验是：判断冗余要看当前真实入口、生命周期和最终生效结果，删除时沿整条功能链收尾，再用与风险相匹配的证据确认边界。本文件记录可复用的方法，不作为新增的强制仓库规则。

## 先区分三种状态

“看不到”不能直接等同于“没有运行”，也不能直接等同于“可以删除”。筛查时可以先把候选放入下面三类：

| 状态     | 含义                                                                           | 需要确认的重点                                                         |
| -------- | ------------------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| 不可见   | DOM、Canvas 或渲染层仍存在，但被实色面板遮住、位于其他层下方，或视觉效果被覆盖 | 是否仍有 `requestAnimationFrame`、定时器、监听器、WebGL 渲染或合成开销 |
| 未挂载   | 当前路由、模板和动态组件入口都没有创建该实现的实例                             | 是否仍有其他页面、动态导入、配置开关或测试工具会挂载它                 |
| 不再运行 | 实例可能仍在，但动画、订阅、渲染器或异步任务已按生命周期条件停止               | 停止条件是否可靠；保留代码是否仍服务于其他状态或入口                   |

例如，普通曲库页面的实色内容曾经遮住主界面流光画布；只看画面会误以为背景不存在。反过来，已经没有调用方的组件即使文件仍在磁盘上，也不代表它还在运行。暂停、隐藏和最小化还要分别检查，因为它们不一定触发相同的生命周期条件。

## 沿真实入口追踪整条链

候选项适合按下面的顺序核对：

`页面或路由 → 挂载条件 → 组件 → 状态与生命周期 → 共享工具或类型 → 样式与资源 → 测试、检查脚本和文档`

搜索一个名称只能提供线索，不能单独证明它是冗余。检查时还要覆盖动态组件、动态类名、持久化开关、路由懒加载和构建脚本。若功能已经收缩，应确认旧状态或存量配置是否仍需要兼容，再决定是否删除状态、类型和迁移逻辑。

纯 TypeScript 导入图也有边界。本轮扫描提醒了三类容易误判的内容：由 `index.html` 单独加载的 `splashController`，源码没有直接导入但属于 `@applemusic-like-lyrics/core` `peerDependencies` 的 Pixi 包，以及只由测试使用、因此没有生产入口的 fixture。它们都应回到实际加载方式、包契约或测试目的核对，不能仅凭“没有生产代码 import”删除。

变量检查还需覆盖配置生成和脚本读取。第一批的 28 个 CSS 变量候选中，有 3 个仍被 `uno.config.ts` 或演示使用，因此保留；只检查源码中的 `var(...)` 会漏掉这些消费者。

“只被测试调用”也需要区分：如果测试还在通过旧包装函数验证现行业务规则，可以评估将断言迁到当前入口；若整理收益很小，就不必单独开工。兼容夹具、性能对照基线和测试辅助实现则可能本来就只服务于测试。测试通过只能说明现有断言通过，不能证明测试入口仍是生产入口，也不能证明未覆盖的路径没有冗余。

共享代码要按实际调用方划边界。旧浮动音量面板被替换后，可以删除只服务于旧面板的 CSS、动画和菜单包装层；仍被内联音量控件使用的滑杆、数值和交互样式要保留。旧桌面歌词实现的专属样式可以清理，但字体不能因旧功能名称而删除，因为唱片室仍在使用它。

功能替换完成后，沿关联链检查旧状态、样式、资源、工具脚本、依赖、测试和文档，删除仅服务于旧实现的部分；共享代码只要还有实际消费者就保留。子代理或分区检查适合提供候选和引用证据，主进程仍需复核并裁定。例如第二批检查曾建议删除 `capture-mac-baseline.mjs`，复核发现目标演示页和对应 DOM 入口仍存在，因此保留。建议本身不等于删除证据。

## CSS 要看匹配关系和最终结果

CSS 中出现 `backdrop-filter`、`filter` 或旧类名，只能说明规则存在，不能说明它正在生效。建议同时检查：

- 选择器当前是否能匹配真实 DOM；
- 是否被更具体的规则、主题规则或媒体条件覆盖；
- 计算样式最终是否仍包含滤镜、透明度和动画；
- 该视觉层是否仍需要采样背后的内容，还是已经改成实色材质；
- 删除后其他弹窗、菜单、封面染色层和全屏播放入口是否仍使用同一共享规则。

本次案例中，播放栏和侧栏已经采用实色或新的表面材质，却曾残留旧的背景滤镜。清理边界应落在播放栏或侧栏专属的残留规则；菜单、全屏播放背景和仍有实际用途的共享浮层样式需要分别核对，不能因为它们也包含 `blur` 就一并删除。

## 证据要分开记录

源码与结构证据回答“代码是否还有入口或匹配关系”，例如导入搜索、路由检查、选择器核对和类型检查。测试证据回答“隔离模块或模拟条件下的行为是否符合预期”，例如单元测试、组件测试和隔离 Electron 对照；它不能代替完整应用运行。完整应用运行证据回答“真实应用是否挂载、绘制、停止或显示”，例如 DOM、computed style、生命周期日志和实际操作路径。性能证据回答“资源消耗是否改变”，需要在相同页面、窗口尺寸、曲目和等待时长下比较 GPU、CPU、帧时间或 DevTools Performance 记录。

这些证据不能互相替代：删除无人引用的文件主要改善维护成本，不能据此声称应用变快；隔离测试或对照通过，不能据此声称完整应用已经验收；看到画面不再显示效果，不能据此声称渲染已停止；源码检查通过，也不能替代运行时和视觉验收。构建检查也要区分编译与产物预算：第一批的默认预算钩子递归统计了 `out` 中已有的 GPU 审计目录，导致总量检查失败；分别检查本次生成的 `renderer`、`main`、`preload` 目录后通过。遇到这类情况，应先辨明失败输入来自本次产物还是既有审计数据，记录两种结果，不为得到绿色结果删除审计材料或随意改变预算阈值。

交付时把三件事说清：本轮实际改动、开始前已经存在的工作区修改、尚未检查或只做了隔离验证的范围。这样可以准确归因差异，也避免把一批清理的完成范围说成全仓已经没有冗余。

## 按收益控制清理范围

优先检查仍在运行却不再服务当前行为的动画、监听器和渲染器，再检查确认无入口的整条旧功能链、无匹配样式和失效工具。命名、内部导出、低风险旧测试标题等收益较小的整理，可以等触碰相关功能时顺手处理；测试若仍保护有效规则，不因入口陈旧而整份删除。

一项清理在其明确范围内已有调用与保留边界证据、必要检查完成、遗留的不确定项如实记录后即可停止。这个停止条件用于避免追求删除数量或“全仓零冗余”的口号；它不替代后续功能变更时对新旧入口的收尾。

## 候选记录格式

后续筛查可以为每个候选保留一条短记录：

> **内容**：要检查的组件、样式、资源或脚本。
>
> **证据**：入口、调用方、匹配关系、生命周期或运行结果。
>
> **保留用途**：仍需服务的页面、状态、兼容输入或共享能力。
>
> **删除边界**：可以删除的专属实现，以及明确要保留的相邻代码。
>
> **验证**：静态检查、运行检查和性能对照分别做了什么，哪些仍未完成。

按这个格式推进时，第一轮适合优先处理“仍在运行但已无用途”的动画、监听器和渲染器，再处理无入口的功能链、无匹配的 CSS 以及失效检查脚本。是否有性能收益仍以实际调用路径和受控测量为准。
