# 6LunaMax 施工提示词撰写规则

本文按用户确定的协作方式制定：6LunaMax 执行边界清楚、步骤明确的施工任务；提示词撰写者负责源码检查、方案设计、选型和实现取舍。

**施工步骤必须细到适合直接执行：每一步都明确在哪里改、怎么改、改完应是什么状态。需要施工者自行作实现决策的步骤，必须继续拆细或补齐决定。**

本规则用于撰写发给 6LunaMax 的施工提示词。任务权限与施工、审查职责沿用所在项目规则；在 Auralis 中，与通用交接规则一起使用，施工步骤的粒度按本文执行。

## 1. 撰写者在交接前完成方案

先阅读当前源码和实际调用方，再写步骤。定位要修改的函数、模板、样式、类型和引用，检查工作区已有修改。历史记录与先前提示词可用于寻找入口，步骤依据须与当前源码一致。

交接前确定以下内容：

- 用户能观察到的最终效果，以及每项效果对应的实现位置。
- 修改文件、保留文件、明确的实现方式和执行顺序。
- 新增或替换的符号名称、代码结构、接口字段和参数值。
- 状态转移、成功与失败分支、取消与资源清理方式。
- 所有配套修改，以及明确保留的行为和约束。

依赖与开源方案由撰写者完成调查和选择，写明采用版本、具体 API、集成方式及许可处理。尺寸、时长、文案、路径等参数在交接前给定。

尚未解决的设计问题由撰写者继续检查，或向用户澄清。发出施工提示词时，方案应已具备完整执行条件。

## 2. 将方案拆成可直接执行的步骤

每一步包含下列信息；简短步骤可合并字段，但操作依据必须完整。

| 信息 | 必须说明的内容 |
| --- | --- |
| 位置 | 绝对文件路径，以及函数名、模板节点、选择器或唯一代码片段 |
| 前提 | 当前应存在的代码形态，或必须先完成的步骤编号 |
| 动作 | 明确的新增、删除、替换或移动操作 |
| 内容 | 要写入的代码、准确参数，或无需设计选择的变换规则 |
| 结果 | 该步骤完成后应存在和应移除的内容 |

用符号和唯一代码片段定位。行号可以辅助定位，步骤不得只依赖会随前序编辑变化的行号。

一项步骤只承载一个明确的变更。涉及多个文件、多个状态分支或多个实现选择时，分别列出步骤。重复机械变更可以合并，但必须列全目标位置和替换规则。

对于新增函数、状态机、异步控制或跨模块接口，提供完整代码片段或完整的分支与数据定义。避免将关键逻辑交给施工者补写。

### 粒度判断

逐步检查：施工者执行这一项时，是否还需要选择算法、参数、结构、名称、兼容策略或错误处理方式？需要，就补齐该决定或继续拆分。

“检查并修复所有引用”应改成具体引用清单。“完善异常处理”应改成各异常的触发条件、执行动作和返回结果。“按需调整”应改成明确的修改内容。

## 3. 列全关联修改和保留行为

删除或替换一个实现时，沿引用链列出受影响位置。按任务实际涉及的内容检查：

- 导入、声明、调用、模板绑定和样式选择器。
- 数组顺序、下标、长度判断及查找条件。
- 类型定义、共享契约、Preload 暴露、IPC 处理与输入校验。
- 状态初始化、成功与失败分支、重试、取消和销毁。
- 动画回调、计时器、事件监听器和资源释放。
- 对应测试代码、语言键、文档和许可记录。

将检查发现转成明确步骤，不能把这份分类清单原样交给施工者自行调查和决定修改。

单独列出必须保留的行为。例如保存按钮调整应说明按钮尺寸、禁用状态、失败输入保留、成功关闭时机和焦点恢复。配套修改应服务于同一目标，范围外发现进入后续任务记录。

## 4. 按依赖安排施工和异常处理

按依赖顺序编号，写明必要的前置步骤。大型任务拆成多个有明确起始条件与交付结果的施工批次，每个批次发出完整步骤。由撰写者确定批次边界与顺序。

施工前核对目标代码与提示词中的起始条件。出现以下情况时，施工者停止当前任务，保留已完成修改，报告并等待补充方案：

- 文件、符号或目标代码不存在，或与描述不符。
- 现有实现或其他会话的修改使既定步骤发生冲突。
- 需要增加清单之外的文件、依赖、接口或实现决策。
- 按既定步骤无法满足目标，或会破坏明确保留的行为。

异常报告写明步骤编号、文件位置、实际代码、与预期的差异、已完成内容及需要撰写者决定的问题。施工者保持现有数据和修改，等待方案补齐后继续。

## 5. 写法与交付

采用 anti-defensive-writing 的写法：先写目标，直接陈述动作和结果；背景只保留影响施工的事实，权限与范围限制集中写一次。

避免“适当”“尽量”“可以考虑”“自行选择”“必要时完善”等会产生实现选择的表达。需要改动的内容给定动作，需要保留的内容写明行为，需要停止的情况给定条件。

提示词须包含完成标准和交付格式。施工者按步骤报告完成情况、明确偏差、重要待验证项，并进行源码差异复查。

在 Auralis 中，施工者完成实现、配套修改和差异复查；测试、类型检查、构建、应用运行及视觉验收由审查者执行。交付标记“实现完成，未测试”；独立验收要求遵循[风险与验收](validation.md)。测试代码的配套修改也应在施工步骤中写明。

### 输出载体与长度阈值

先完成提示词，再按完整正文的长度选择输出载体：

- 正文达到 **4,000 个字符**或 **100 个非空行**，任一条件满足时，保存为 UTF-8 Markdown 文档。
- 正文少于 4,000 个字符且少于 100 个非空行时，直接在对话中输出完整提示词。
- 用户明确指定输出载体或保存路径时，遵从用户要求。

计数包含提示词内的标题、正文、路径、代码块和 Markdown 标记，不包含对话中的引导说明；换行统一按 LF 计数，字符数包含空格和换行，非空行按源文本计算，不按界面自动折行计算。一次交付包含多个施工批次时，按全部提示词正文合计判断。保留完整步骤与代码，不通过压缩内容、合并行或拆分消息规避阈值。

文档默认保存至 `docs/handoffs/YYYY-MM-DD-<任务英文短名>-construction.md`，日期采用用户当前时区；同一任务修订时更新原文档，保留与本次修订无关的已有内容。已有同名文档属于其他任务时，使用 `-2`、`-3` 等后缀另建文件。

保存后，在对话中提供文档的绝对路径 Markdown 链接，并用一至三句话说明目标、批次范围和关键决定；完整提示词以文档为准，不在对话中重复全文。落盘并复查内容后再交付链接。

## 6. 标准模板

模板中的占位内容由撰写者在发送前填写完整。

```text
你是本轮施工者。按以下确定方案完成实现和差异复查。

项目：<绝对路径>
规则入口：<AGENTS.md 与本任务相关规则的路径>

目标与完成标准：
1. <用户能观察到的结果>
2. <可据源码核对的完成条件>

当前源码起始条件：
- <文件、符号或代码片段，以及已确认的现有行为>
- <涉及本任务的已有未提交修改及保留方式>

修改范围：
- <逐一列出允许修改的文件>

必须保留：
- <具体行为、接口、数据和资源清理约束>

施工步骤：
1. 位置：<文件与唯一定位标识>
   前提：<当前代码或前置步骤>
   动作：<准确的编辑操作>
   内容：<准确代码、参数或机械变换规则>
   结果：<完成后的明确状态>
2. <按相同粒度列全后续与配套步骤>

异常处理：
源码起始条件不符、步骤冲突或出现未覆盖的实现决策时，停止任务。
报告步骤编号、实际代码、差异、已完成修改和需要补充的决定，等待补充方案。

施工复查与交付：
- 按步骤核对最终差异、保留行为和改动范围。
- <写明本项目施工阶段允许的操作与测试、验收职责>
- <写明交付状态和待验证内容>
```

## 7. 粒度示例：双圈改为单圈并放大勾

下面示例展示步骤粒度。用于实际任务前，撰写者须重新核对源码起始条件。

假定起始条件：`SaveProgressIcon.vue` 中有 `outer`、`inner`、`check` 三个路径，`segments` 数组按此顺序初始化，成功勾由 `segments[2]` 绘制。图标大小为 20 × 20 px，`viewBox` 为 `0 0 120 120`。

目标：保留一个圆形加载轨迹；成功勾横向占图标区域约 75%；按钮尺寸、成功后的 300 ms 停留、取消和销毁清理保持现有行为。

所有步骤作用于 `D:\VSCode\Auralis\src\renderer\shared\feedback\SaveProgressIcon.vue`：

1. 删除模板中 `ref="inner"` 的 `<path>` 节点，保留 `outer` 和 `check` 节点。
2. 删除脚本中的 `inner` ref 声明及整个 `spinInner()` 函数。
3. 在 `onMounted` 的路径检查中，删除 `!inner.value` 条件；在 `drawCheck` 的路径检查中做同样删除。
4. 将初始化数组 `[outer.value, inner.value, check.value]` 替换为 `[outer.value, check.value]`，保留原来的 Segment 构造方式。
5. 删除 `onMounted` 中的 `spinInner()` 调用，保留 `spinOuter()` 及减少动效分支。
6. 将 `complete()` 中的 `segments.length !== 3` 改为 `segments.length !== 2`。
7. 删除 `drawCheck` 中设置 `inner.value.style.visibility` 的语句。
8. 删除成功收尾分支中原内圈的 `segments[1].draw('100%', '100% + 0.1', 0.12, ...)` 调用，保留外圈收尾回调。
9. 将绘制勾的 `segments[2].draw(...)` 改为 `segments[1].draw(...)`；将起止参数改为 `0`、`'100%'`，保留原时长和完成回调。
10. 将 `check` 节点的 `d` 替换为 `M 15 60 L 48 93 L 105 27`，保留图标尺寸、viewBox、线宽、描绘和轻微弹入动效。
11. 按以上位置复查差异：`inner` ref、模板节点、函数、调用及可见性操作均已删除；数组有两个路径，勾使用下标 1；AbortSignal、卸载清理和后台结束兜底保持原逻辑。

这组步骤同时给定路径几何与完整描绘范围，避免施工者只放大 SVG 外框，或改大路径后仍只显示末尾 50 个长度单位。

## 8. 发送前检查

- 已阅读当前源码与调用方，所有目标位置和起始条件可定位。
- 方案、名称、参数、接口与错误分支已经确定。
- 每一步能直接编辑，无须施工者自行作实现决策。
- 关联修改已逐项列入步骤，步骤顺序符合依赖。
- 修改范围、保留行为、异常停止条件与交付标准明确。
- 模板占位内容已填写，施工与审查职责符合项目规则。
- 已按完整正文的字符数与非空行数选择输出载体；需要文档时已保存、复查并提供链接。

发现缺项时，由撰写者补齐后再交接。
