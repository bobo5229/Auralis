# 轻量风险验收

适用：修改后的本地验收与发布验证。只读探索、解释和方案讨论不要求运行应用检查。

Auralis 是单人开发、仅开发者本人使用的个人项目。本地验收以避免个人数据损坏、应用无法启动和
核心功能明显回归为目标，不追求团队协作、合并门禁或发布级证据完整性。验收用于降低本次改动的
实际风险，不用于完成固定流程；默认采用成本最低且能覆盖主要风险的检查，达到目标后立即停止。

## 选择等级

| 等级   | 典型改动                                                                       | 默认验证                                                                        |
| ------ | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------- |
| 轻微   | 文档、文案、局部 CSS、颜色、间距、圆角、动画和直接可见的布局调整               | 检查本次差异；方便运行时手动查看受影响区域，否则注明未视觉验证                  |
| 常规   | Renderer 局部行为、路由、普通业务逻辑、共享 composable、可恢复的窗口行为       | 从定向测试、`typecheck`、手动操作中选择最有价值的一项或两项，不默认运行完整检查 |
| 高风险 | 数据库迁移、音频标签写回、文件删除或移动、扫描器、IPC 安全边界、原生依赖、发布 | 使用隔离数据验证关键正常与失败路径；按实际影响增加测试、构建、启动或产物检查    |

- 按失败后果、可恢复性和人工发现难度分级，不按文件数量、代码行数或“修改了共享组件”机械升级。
- 普通 UI、窗口几何和样式改动不会因为涉及 Electron 就自动成为高风险。
- 影响真实音乐文件、数据库或不可逆状态的改动，即使代码很少也属于高风险。
- 每次任务不必征求用户选择等级，也不必撰写验收计划；需要升级时用一句话说明具体风险。
- 开发中的中间状态不要求提前完成最终验收；准备结束当前修改时再做最小充分验证。

## 人工验收

- 对直接可见、容易复现、失败后不会损坏数据且能够立即回退的 UI 问题，开发者实际使用确认可以
  替代自动化运行时验收、截图和 Electron smoke test。
- 用户已经确认某个场景正常时，不为补充“交付证据”重复要求截图、构建、smoke 或自动化检查。
- 视觉检查只覆盖本次实际影响的页面、状态和断点，不执行全应用矩阵。只有共享规则确实传播到多个
  owner 时才抽查相应消费者。
- 没有方便的 GUI 环境时，注明“未进行视觉验证”即可；不搭建额外截图平台，也不用单测冒充视觉结论。
- 自动化测试优先保护人工难以观察、容易复发、失败影响较大或可能损坏个人数据的逻辑。

## 测试与命令选择

以下命令都是按需入口，不是顺序执行的清单。脚本定义以 `package.json` 为准。

| 用途                     | 命令                                                       |
| ------------------------ | ---------------------------------------------------------- |
| 定向普通测试             | `npm.cmd run test:unit -- <实际测试文件或路径>`            |
| 普通测试集合             | `npm.cmd run test:unit`                                    |
| Electron ABI 原生测试    | `npm.cmd run test:native`                                  |
| 静态视觉作用域检查       | `npm.cmd run test:library-scope`                           |
| 类型契约检查             | `npm.cmd run typecheck`                                    |
| 定向 lint                | `npm.cmd exec -- eslint --max-warnings 0 <实际文件>`       |
| 定向格式检查             | `npm.cmd exec -- prettier --check <实际文件>`              |
| 全仓格式检查             | `npm.cmd run format:check`                                 |
| 完整测试                 | `npm.cmd test`（包含普通、native 和静态视觉作用域检查）    |
| 全仓 lint                | `npm.cmd run lint`                                         |
| 构建                     | `npm.cmd run build`（含类型检查及当前 pre/postbuild 步骤） |
| 已有构建的 Electron 冒烟 | `npm.cmd run smoke:electron`                               |

- 修改已有受测逻辑时优先运行现有定向测试；不要求每个 bug、样式调整或直接可见行为都新增回归测试。
- 只有逻辑容易复发、人工验证成本高或失败影响较大时才新增测试。数据测试使用隔离的临时数据，不能修改
  用户真实曲库或音乐文件。
- `typecheck` 主要用于 TypeScript 契约、公共接口、跨模块调用或较广泛的代码改动，不作为每次局部修改
  的默认步骤。
- build 主要用于入口、Preload、IPC 接线、构建配置、依赖或只在生产构建出现的问题；已成功构建时不
  重复运行单独的 `typecheck`。
- Electron smoke test 默认不运行。仅在修改启动流程、窗口创建、Preload、安全策略、正式构建接线，
  或相关问题无法方便地人工确认时选择运行。普通布局、样式和可直接手动验证的窗口行为不要求 smoke。
- 完整测试、全仓 lint、全仓格式检查、smoke、打包和产物验证只在准备长期使用的稳定版本、
  发布、高风险数据/依赖改动，或具体故障只能由对应检查发现时运行。

## 提交与推送的验证

提交或推送不额外触发固定的全仓门禁。按本次改动的风险选择验证，并在提交前检查将要提交的差异：

- 轻微改动通常检查差异即可；代码改动按需对涉及文件运行定向测试、格式或 lint 检查。
- 修改类型契约、公共接口或跨模块调用时考虑 `typecheck`；高风险改动仍验证关键正常与失败路径。
- 已有检查覆盖最终差异时直接复用；若之后修改代码，只补查受影响部分。

## 文档、CI 与当前任务的关系

- TECHDOC、PRD、历史交付记录、截图清单和测试矩阵是背景与参考，不自动成为当前任务的完成门槛。
  只有用户明确要求按某份文档施工或执行指定矩阵时，才将其中验收项纳入本轮范围。
- GitHub CI 和本地日常验收相互独立。CI 可以保留完整检查，不要求每次本地提交先运行同一套命令；
  本规则也不授权修改、跳过或禁用 CI。
- 功能状态以当前源码、路由、实际使用和已运行的检查共同判断，不能只依据历史文档中的完成度。

## 去重、失败与交付

- 在“检查差异、定向测试、`typecheck`、手动操作”中选择最便宜且最相关的证据；通常一项或两项即可。
- 后续修改使相关检查结果失效时，只复查受影响部分；不为交付措辞重复执行检查。
- 与本次无关的历史失败或环境限制单独说明，不默认接手修复。检查未运行或无法运行时如实记录，不能
  将静态检查描述为运行或视觉验收通过。
- 最终只需简述实际修改、已做检查和仍然重要的风险。低风险未验证项不阻止个人开发继续进行；涉及
  真实数据损坏、应用无法启动或不可逆操作的关键风险未确认时，不宣称高风险修改已经完成。

默认流程可以概括为：检查本次差异，选择一个最便宜且最相关的验证，说明实际结果，然后结束。
