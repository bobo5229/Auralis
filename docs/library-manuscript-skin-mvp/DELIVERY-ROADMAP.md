## 1. 交付结论

Auralis 手稿皮肤已经完成从单页 MVP 到多页面视觉系统的第一轮建设：

- 全部歌曲页已经具备纸面、账册列、档案页眉、唱片目录卡、搜索、右键菜单、元数据编辑和键盘操作的完整手稿体验；
- 专辑目录和专辑详情已经接入同一视觉偏好，并保持专辑 identity、路由、播放和异步视觉效果生命周期不变；
- 归档页的代码实现与工程审查已经完成，音乐日历、Music DNA、排行、年度总结及其自有浮层已经形成统一档案视觉；
- 共享 token、路由呈现解析器、Teleport owner scope、虚拟滚动几何和静态作用域检查已经成为后续扩展的基础设施；
- 现代流光界面仍是完整、独立的视觉分支，切换手稿皮肤不会改写播放状态、曲库数据或数据库行为。

当前可以把产品状态概括为：**核心浏览链路已覆盖，工程基础已建立；既有视觉与功能人工验收已按用户确认回填；Phase 9–11 容量门禁仍延期；Phase 14 工作树尚未提交；Phase 15 已冻结基线并开始覆盖普通与智能歌单。设置、应用外壳与播放器表面尚未纳入手稿覆盖。**

### 3.1 已关闭的核心能力

- 单一 `modern | manuscript` 偏好源与安全持久化；
- 明确的 route-name 呈现边界，不使用路径前缀推断；
- Library、Albums、Album Detail 和 Archive 的页面级手稿作用域；
- Library、Albums 和 Archive 自有 Teleport 浮层的 owner scope；
- 暖白纸面、墨色文字、暗红强调、衬线标题、细线分隔和近直角几何；
- 平铺 44px、封面曲目 40px、封面 250px 等虚拟滚动几何契约；
- 搜索定位、选中、播放、暂停、焦点、缺失元数据和缺封面表达；
- 现代专属 artwork canvas、ResizeObserver、pointer listener 的启停与失效保护；
- 图片 `loading='lazy'`、`decoding='async'` 和现有 artwork URL 管线；
- Vitest、三语 locale parity、视觉作用域静态守卫、类型检查、lint 和生产构建门禁。

### 3.2 尚未关闭的交付债务

## 4. 后续开发顺序

后续优先完成现有路由覆盖，再扩展跨页面外壳和播放表面。每个阶段必须单独设计、实现、审查和验收，不应一次性把 `data-visual-style` 提升到 `html`、`body`、`#app` 或整个应用根节点。

### Phase 15：覆盖普通歌单与智能歌单

**为什么先做**：两个路由复用已经成熟的 `LibraryPage.vue`，能够以最低结构风险补齐曲库家族，同时验证视觉系统是否真正支持“同组件、不同产品语义”。

**实现方向**：

- 扩展 Library presentation resolver，只允许 `library`、`playlist` 和 `smart-playlist` 三个明确路由消费共享偏好；
- 为普通歌单与智能歌单设计不同于“全部歌曲档案”的页眉身份、数量摘要和只读 / 可编辑状态；
- 复用账册行、唱片目录卡、缺失元数据、搜索和右键浮层，不复制第二套 CSS 或状态源；
- 保留歌单队列作用域、智能规则、添加 / 移除、元数据编辑和滚动锚点行为；
- 增加路由解析、歌单身份、空状态、浮层作用域和虚拟几何测试。

**完成标准**：三种 Library 路由都能切换手稿风格，彼此页眉和行为语义可辨；modern 无回归，切换路由不清除用户偏好。

### Phase 16：覆盖设置页并集中外观入口

**为什么第二步做**：页面路由覆盖完成后，需要一个稳定、可发现的外观管理位置，避免用户只能在内容页寻找切换控件。

**实现方向**：

- 只为 `settings` 路由增加显式 presentation resolver 和页面作用域；
- 把外观设置区设计为纸张样本、文字层级与当前选择的预览，但继续写入唯一 `useVisualStyle` 状态源；
- 手稿化侧栏分组、设置 section、开关、选择器、路径列表、扫描进度、错误和确认状态；
- Settings 自有 Dialog / picker 使用 owner scope，不把规则扩散为全局表单样式；
- 保持曲库目录、扫描、语言和 PlayerBar 材质等设置行为不变。

**完成标准**：用户可以从设置页理解并切换视觉风格；设置控件、扫描流程、错误恢复和键盘焦点在两种风格下都完整可用。

### Phase 17：连接应用外壳与 Sidebar

**为什么此时做**：当所有主要内容路由都有手稿版本后，才适合让页面之间形成连续的视觉环境。过早修改外壳会让尚未覆盖页面处于半手稿状态。

**实现方向**：

- 设计 shell presentation 层，但仍从唯一视觉偏好派生，不创建新的“外壳皮肤”开关；
- 覆盖 Sidebar、导航选中态、歌单树、工具入口和主内容边界；
- 手稿模式停止消费不必要的窗口封面调色与流体背景，切回 modern 时恢复；
- 为 Sidebar 自有创建歌单、智能规则等浮层增加明确 owner scope；
- Windows 原生标题栏保持系统提供，不伪造手稿最小化、最大化或关闭按钮。

**完成标准**：在各手稿页面间导航时视觉连续；进入 modern 或未覆盖的独立播放表面时没有 token、背景或事件监听泄漏。

### Phase 18：覆盖 Now Playing 与 PlayerBar

**为什么独立成阶段**：它们是持续驻留、强交互、封面调色驱动的播放表面，风险高于普通页面；同时 PlayerBar 与 Miniplayer 必须继续严格隔离。

**实现方向**：

- 基于现有 playback composable 派生视觉状态，不新增播放器 store；
- 为 Now Playing 和 PlayerBar 设计手稿式曲目信息、进度尺、传输控制、音量、队列与模式 popover；
- 明确手稿状态是否停止封面色板提取、玻璃 blur 和流体动效，切回 modern 后恢复且不重复绑定；
- 保留播放、暂停、seek、音量、队列、循环、随机和桌面歌词同步；
- 所有 popover 使用播放器 owner scope，并覆盖键盘、focus-visible 与 reduced-motion。

**完成标准**：主窗口从内容页到常驻播放控制形成完整手稿语言；播放行为、进度精度和 modern 材质无回归，Miniplayer 未被误改。

### Phase 19：覆盖全屏播放器

**为什么排在 PlayerBar 之后**：全屏播放器是自封闭的深色 artwork 视觉域，包含歌词、背景和更多动画，应该建立在播放器表面 token 和生命周期契约稳定之后。

**实现方向**：

- 为 fullscreen route / overlay 建立独立 owner scope，不依赖根 token 的偶然继承；
- 将流体 artwork 背景替换为手稿纸页、歌词页、唱片资料和播放状态编排；
- 明确 canvas、歌词滚动、进度同步、指针与键盘监听在切换和关闭时的清理；
- 保留歌词时间轴、播放控制、退出全屏与 reduced-motion 行为。

**完成标准**：全屏播放器能独立往返两种视觉风格，没有隐藏 canvas 或监听残留，歌词同步和播放控制保持一致。

### Phase 20：评估并覆盖 Miniplayer

**为什么最后处理主窗口模式**：Miniplayer 复用主 `BrowserWindow`，但 Renderer、尺寸和交互职责独立；原生标题栏会占用其窗口空间，视觉扩展前应先完成真实窗口尺寸验收。

**实现方向**：

- 先确认保留“同一 BrowserWindow 的迷你模式”还是拆成独立物理窗口；这是架构决策，不应由 CSS 顺带决定；
- 若保留现状，为 `MiniPlayer.vue` 建立自己的 presentation、token 和几何门禁；
- 若拆窗，先完成窗口生命周期、bounds、always-on-top 和状态同步设计，再实现皮肤；
- 不复用 PlayerBar DOM，不因名称相近而共享不合适的布局样式。

**完成标准**：Miniplayer 的封面、控制、窗口尺寸和原生标题栏关系明确；两种皮肤可切换且不影响主窗口 PlayerBar。

### Phase 21：桌面歌词与最终统一交付（可选）

桌面歌词是独立窗口和独立阅读场景，是否需要手稿皮肤应由产品体验决定，而不是默认继承主窗口偏好。若确认覆盖，再单独设计字体、背景透明度、拖拽区、锁定、点击穿透和多屏 DPI 行为。

最终统一交付应补齐跨页面截图、视觉回归基线、所有 owner scope 检查、键盘巡检、Windows 100% / 125% / 150% 缩放，以及 modern 与 manuscript 连续往返压力测试。

## 6. 后续阶段统一交付门禁

每个新 Phase 至少满足以下条件，才可写为“工程完成”：

- 作用域由明确路由名或明确 owner surface 决定；
- 不新增 visual-style 状态源或 localStorage key；
- modern 视觉和产品行为保持不变；
- Teleport 浮层有 owner scope，不使用无边界全局选择器；
- 现有播放、队列、搜索、路由、元数据和扫描语义保持不变；
- 图片保持 lazy / async 契约，昂贵视觉计算在手稿状态真正停止；
- 动效遵守 `prefers-reduced-motion`，监听器、observer、timer、rAF 和异步图片工作可清理；
- 三语 locale key 一致，中文文件通过严格 UTF-8 字节解码；
- `npm.cmd test`、`npm.cmd run typecheck`、`npm.cmd run lint`、`npm.cmd run build` 与 `git diff --check` 通过；
- 完成与该表面匹配的 Electron 人工矩阵后，才可从“工程完成”更新为“完全交付”。

## 7. 关键边界

- 手稿皮肤是 Renderer 视觉偏好，不是 light / dark 主题，也不是 PlayerBar 材质偏好。
- 不把页面手稿规则提升为未经设计的全局 skin；跨表面覆盖按 Phase 显式开放。
- 不为了视觉覆盖改变 Repository → Service → Typed IPC → UI 数据流。
- 不让手稿显示文案替换 `Unknown Artist`、`Unknown Album` 等内部 identity。
- 不改变虚拟滚动尺寸而不同步 TypeScript metrics、CSS 和定位公式。
- 不把 PlayerBar 与 Miniplayer 混为同一个组件或交付范围。
- 不重建 Renderer 自绘窗口控制；Windows 原生标题栏始终由操作系统负责。
