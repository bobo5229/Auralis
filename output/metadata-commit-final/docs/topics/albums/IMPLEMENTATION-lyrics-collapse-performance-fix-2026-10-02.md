# 历史施工方案：专辑列表页收起歌词动画性能修复

日期：2026-10-02  
状态：历史施工计划；后续实现已替换本文的移动缩放方案与任务清单。
适用入口：普通专辑列表页，在 Playbar 点击歌词展开或收起按钮。  
执行方式：单会话、分阶段施工；每阶段完成定向验证后继续。

> 当前源码说明见[歌词面板收起与专辑网格同步过渡：当前实现](TECHDOC-lyrics-collapse-album-grid-sync-2026-09-30.md#当前实现-2026-10-08)。当前实现采用固定几何的两组网格淡切、Sidebar 轻移淡切、歌词 transform 和 Playbar 位移/淡切；本文的阶段任务、测试要求和交付模板只记录当时计划，不是新待办。隔离合成数据对照显示绘制相关开销下降，但触发附近仍有约 33ms 帧间隔/部分帧更新标记；真实曲库与物理窗口性能尚未完全验收。

本文将修复拆成边界明确、可以逐项核验的任务，适合交给用户指定的 GPT6Luna Max 执行。这里采用的是小步修改、显式契约、局部测试和结果门槛，不对该模型的能力或性能作基准判断。本文本身是施工说明；执行者获得用户实施授权后再修改产品代码。

## 1. 目标与完成定义

修复用户报告的“在专辑列表页点击 Playbar 收起歌词按钮时，收起动画严重掉帧”。保留现有专辑、歌词面板和 Playbar 的同步过渡，以及展开、快速反向、滚动锚点和页面切换行为。

完成结果必须同时满足：

- 过渡层只管理当前可见的有效动画项，脱离 DOM 的旧项不会继续进入逐帧更新。
- 准备阶段已经创建的卡片快照可用于目标提交后的动画，避免无理由地整批删除、重新深拷贝。
- 专辑目标布局在准备阶段提交；动画中没有网格重算、卡片几何读取或虚拟器主动测量。
- 歌词、网格、Playbar 在同一动画时钟下开始和结束，结束时没有第二次可见重排。
- 同一环境的前后录制证明主要卡顿得到改善，并满足第 10 节指标；达不到时按证据继续定位。
- 自动化回归、实际 Electron 行为检查及最终差异复查完成，交付明确记录证据。

只修复一个数组遗漏、只通过单测或只看到一次流畅动画，都不足以宣布用户问题已经解决。

## 2. 当前事实和诊断边界

### 2.1 以当前实现为起点

背景文档：[歌词面板收起与专辑网格同步过渡技术方案](TECHDOC-lyrics-collapse-album-grid-sync-2026-09-30.md)。其中关于改造前逐帧列宽变化和动画后提交网格的描述属于历史背景。

2026-10-02 检查的工作区已经包含以下实现：

- `App.vue` 的 `runAlbumLyricsTransition()` 编排专辑页独立事务。
- `createLyricsAlbumTransitionCoordinator()` 管理 revision 和阶段。
- `AlbumsPage.vue` 提供 prepare、commit、render、finish、cancel 接口。
- `useAlbumGridLayout` 提供 begin、commit、end 事务接口，阻止动画中自适应重算。
- `AlbumGridTransitionLayer.vue` 使用 DOM 副本承担可见卡片移动。
- 专辑页路径在动画前将 `lyricsProgress` 提交到目标值，逐帧改变的是展示层。

执行者应保留并改进这条链路。不要按旧文档重新实现协调器，也不要将专辑页退回逐帧改变 Grid 列宽的通用路径。

### 2.2 证据分级

| 编号 | 结论                                                   | 证据性质                     | 施工含义                                |
| ---- | ------------------------------------------------------ | ---------------------------- | --------------------------------------- |
| F1   | `mount()` 删除子节点但没有清空 `items`；后续继续 push  | 源码可确认的生命周期缺陷     | 必修，并新增覆盖真实管理逻辑的回归测试  |
| F2   | 正常事务在 prepare 和 commit 两阶段调用 `mount()`      | 源码可确认的调用关系         | 单次操作即可出现 F1，不要求快速连点     |
| F3   | 旧卡片采集深拷贝一次，两次 mount 内又分别深拷贝        | 源码可确认的重复工作         | 缩减快照构建，明确节点所有权            |
| F4   | `renderProgress()` 逐帧修改根层 `clip-path`            | 源码可确认；具体渲染成本待测 | 修正注释，用 trace 决定是否改变裁剪方案 |
| F5   | 列数变化会改变卡片所在父行，可能导致组件重新挂载       | 结构支持的风险；数量待测     | 统计 mount/unmount，不能先假定全量重建  |
| F6   | Playbar 深拷贝、卡片阴影与透视、图片栅格化可能参与卡顿 | 性能假设                     | 在前述修复后依据耗时排名选择优化        |

当前没有 Performance trace、实际帧率、GPU 利用率或前后对照结果。F1 是确定性缺陷，但尚不能断言它独自解释严重掉帧。

### 2.3 F1 的准确影响

设旧视口有 N 张有效卡片，目标视口新增 M 张：准备阶段登记 N 项；提交阶段移除旧节点，再登记 N＋M 项，但旧 N 项仍在数组中。稳态循环约处理 2N＋M 项，有效挂载项只有 N＋M 项。

对脱离 DOM 的节点写 style 仍有 JavaScript 工作量并保留对象引用，但不能据此声称这些节点继续参加页面布局、绘制或 GPU 合成。完整事务结束的 `clear()` 会清空数组，因此这也不等同于跨完整操作永久泄漏。动画中反向重建时，积累路径需要额外覆盖。

## 6. 阶段 B：修复失效动画项

### B1. 最小修复

在现有 `mount()` 的替换语义中，重建 DOM 时同步丢弃上一批 `items`。检查 items 清空和 `replaceChildren()` 的相对顺序，让渲染循环始终只持有当前 root 的子项。

保留 `clear()` 对 viewport、数组、DOM 和 display 状态的完整重置。不能只在 `renderProgress()` 跳过 `!isConnected` 来掩盖所有权错误；运行期连接检查可以作为额外保护，但不代替释放旧引用。

阶段 C 会将正常 prepare/commit 改为复用语义，届时不再机械地在 commit 清空全部有效项。本阶段明确修复旧的“替换却保留登记”问题，后续架构必须保持同一不变量。

### B2. 最小行为回归

构造 3 个旧项和 1 个新增目标项：

1. 首次挂载旧项，登记和连接数量均为 3。
2. 再次挂载目标计划，有效数量为 4，而不是 7。
3. 调用 `renderProgress(0.5)`，第一批被移除节点的 style 写入计数不再增长。
4. 连续替换 5 次，数量只与当前集合有关。
5. `clear()` 后登记为零、子节点为零、root 隐藏；重复 clear 安全。

使用真实产品控制器或实际组件暴露的方法。不要在测试里重新写一个“正确的 items 数组”，再测试该替代实现。

阶段完成条件：上述测试修复前失败、修复后通过；记录失败原因和验证结果；快速收放功能仍正常。

## 7. 阶段 C：复用快照，减少动画前集中工作

### C1. 首选设计

将当前重复 `mount(from, to)` 分成“准备源展示”和“提交目的地”两个含义明确的操作。推荐内部接口如下，名称可按项目风格调整：

```ts
prepareSources(fromViewport, sources): void
commitTargets(toViewport, targets): void
renderProgress(progress): void
captureVisuals(): AlbumTransitionVisual[]
captureViewport(): AlbumTransitionRect
clear(): void
```

页面对 App 的五个公开事务接口可保持不变。只调整 `AlbumsPage.vue` 与展示层之间的接口，控制修改范围。

### C2. 节点所有权

推荐让采集函数提供已经脱离真实列表的快照节点，展示层取得这些节点的所有权并只挂载一次。另一个可接受设计是采集函数提供真实源引用，展示层在 prepare 时复制一次；两者选一种，类型和注释必须一致。

无论选哪种，必须满足：

- 真实 `.album-card` 从不被从虚拟列表移走。
- `sanitizeSnapshot` 的“复制”和“清理属性”职责拆清楚；不得在已拥有副本上再次无条件深拷贝。
- 对源副本清理 id、tabindex 和交互属性，只发生在获得所有权时。
- 准备阶段挂载的旧快照在 commit 后继续使用，保持节点身份。
- 只有新增可见目标创建新的终点副本，匹配 key 只更新 destination。
- 暂存的真实节点引用不跨越会卸载这些节点的布局提交；需要跨越时先创建独立快照。
- 副本不创建 Vue 组件实例、订阅或 IntersectionObserver；DOM clone 本身也不会复制 Vue 的 JS 监听器和组件生命周期。

### C3. Prepare 的顺序

1. 停止旧时钟并检查当前事务；反向场景先按 C5 捕获当前视觉。
2. 批量读取旧 viewport 和可见卡片几何；先读后写。
3. 创建或接收源副本，挂载旧画面；设置源 wrapper 的尺寸、位置和初始 opacity。
4. 锁定几何更新并隐藏真实列表，旧展示层保持可见。
5. 给后续 commit 保存当前 viewport 和源项信息。

读阶段可以采集多个卡片矩形；重点是避免每个卡片循环中先插入新节点、再读下一个真实卡片，从而交错触发布局。

### C4. Commit 的顺序

1. 沿用 App 的终态歌词列宽提交与 nextTick 门禁。
2. 调用现有 `commitGridTransitionTarget()`；保留虚拟器测量和 scrollTop 恢复顺序。
3. DOM 和锚点就绪后批量读取目标 viewport、目标可见卡片矩形。
4. 按稳定 key 计算匹配、离开和新增集合。
5. 复用旧 wrappers，更新 destination；仅新增目标创建副本。
6. 更新根层两端 viewport 的包围范围和裁切。
7. 若根层 origin 变化，批量重写源 wrapper 相对 origin 的初始 left/top，使屏幕起点不变。
8. 写入统一初始帧，确认真实目标布局未裸露，再启动时钟。

正常 commit 不调用整层 `replaceChildren()`。若实现仍需要整体替换，必须给出不可复用原因并证明复制量已达到目标；不得只把重复复制换一个函数名。

不要为减少 nextTick 次数而直接删掉等待。先证明目标 DOM、总高度和滚动位置已经稳定，再合并冗余边界；若需要等待一个绘制帧，旧快照必须覆盖这个等待期。

### C5. 快速反向

反向只捕获当前连接且可见的有效 wrapper。捕获坐标为当前屏幕矩形，opacity 为当前可见值；新的 transform 从该视觉起点计算，不能重复应用上一次缩放。

先完成捕获，再清理旧节点和旧数组。捕获集合仅来自当前 root；不得因历史 items 产生重复 key 或隐形源。瞬时 alpha 接近零的项可沿用现有阈值排除。

新 revision 的 prepare 和 commit 各自检查有效性。旧 Promise 返回、旧动画 complete 或取消回调不能清除新事务。反向发生在 preparing 和 animating 两个阶段，都需要测试。

### C6. 本阶段效果门槛

暖缓存普通操作中，旧卡片从当前三轮深拷贝缩减为一轮；已有源 wrappers 在目标提交后保持身份。新增目标按需要复制一次。反向重新捕获属于新事务的必要工作，单独计数。

重新录制核心基准组，比较准备耗时、节点创建量、首帧和运动期帧情况。若用户卡顿已解决且满足验收指标，阶段 D 仅执行证据核对，不继续扩大改造。

## 8. 阶段 D：按剩余耗时选择优化

每次只选择一个有证据支持的主要瓶颈，修复后复测同一基准组。下面是决策分支，不是必须全部实施的清单。

| 观察到的主耗时                                | 下一步                                                        | 必须保留的约束                                 |
| --------------------------------------------- | ------------------------------------------------------------- | ---------------------------------------------- |
| 准备阶段仍集中 Layout/Recalculate Style       | 梳理 App 与页面的读写顺序，缓存本事务已读取矩形，批量设置样式 | 目标几何准确、锚点和 CSS 响应式结果正确        |
| 快照节点构建或样式计算占主导                  | 缩小快照到必要展示内容，先局部对比普通与透视模式              | 封面、文字、阴影、内部 3D 外观及无障碍隔离不变 |
| `clip-path` 更新对应明显 Paint/Raster 峰值    | 在隔离对照中固定裁剪以测贡献，再评估保持移动边界的替代实现    | 不让专辑穿透歌词、侧栏、页头或 Playbar         |
| Playbar 快照成本明显                          | 复用准备副本，检查当前重复 clone 和整套自定义属性复制的必要性 | 材质、按钮断点、宽度变化与最终交互正确         |
| 列数变化时卡片 mount/unmount 和图片处理占主导 | 先检查多余更新、palette 调用与缓存命中，再评估更小的复用调整  | 不扩大成曲库加载或全局卡片重构                 |
| 运动期 JS 持续占主导                          | 确认无重复项、无读布局、无响应式逐帧渲染，再评估局部动画 API  | 同一时钟、反向和取消语义仍成立                 |
| 清理阶段出现长任务或可见跳动                  | 检查 endTransition 的重复 update、列表显露顺序和副本移除      | 稳定终态一次显露，所有资源释放                 |

`transform`、`opacity`、`clip-path` 的实际合成方式以当前 Electron trace 为准。不能仅凭属性名断言 GPU 路径，也不能将诊断时禁用 blur、裁剪、歌词或硬件加速直接作为正式修复。

若最终需要调整裁剪，先记录原始视觉边界。替代方案应在固定大小外层、必要遮罩或其他局部结构中证明同等边界效果；不要未经验证对整层做 scaleX，因为封面、文字和透视会一起变形。

## 9. 自动化验证设计

当前 Vitest 默认 `environment: 'node'`，部分组件使用自定义 renderer。没有默认真实浏览器布局，也不应直接编写依赖 jsdom 或浏览器全局对象的测试然后增加整套依赖。

### 10.2 性能指标

以下沿用背景方案的实施目标，属于验收目标而非当前测量结果：

- 暖缓存点击到首次可见反馈 P95 ≤ 50ms。
- 暖缓存动画窗口 dropped frames 比例 < 5%，以 trace 中可用帧呈现信息为依据。
- 从点击到清理结束，无归因于本次过渡的 ≥ 50ms 主线程任务。
- 无打断事务的目标几何提交一次；逐帧阶段 measure、卡片几何读取、clone、DOM 新建计数为零。
- 准备与提交完成后，登记动画项和当前连接动画项相等。
- 完整清理后，卡片快照、Playbar 快照、事务监听器及活动时钟归零；真实交互状态恢复。

按实际刷新率采用帧预算，60Hz 约 16.7ms、120Hz 约 8.3ms。使用 rAF 间隔只能提供辅助信号，不可直接等同 dropped frames。trace 不提供可靠呈现计数时，将该指标标记为未验证，并给出已有信号。

20 次操作的 P95 使用明确的统计方式，例如最近秩法 `sorted[ceil(0.95 * n) - 1]`。样本少时同时给出中位数、最大值和原始样本数量；收起与展开分开统计。

## 11. 执行顺序与停止条件

| 顺序 | 任务               | 完成时必须留下的结果                                   |
| ---- | ------------------ | ------------------------------------------------------ |
| A    | 核对源码与记录基线 | 当前链路、环境、trace 或明确运行阻碍                   |
| B    | 修复失效 items     | 最小修复、真实逻辑回归测试、前后计数                   |
| C    | 减少重复快照构建   | 所有权说明、prepare/commit 复用、反向测试              |
| D    | 定向优化剩余瓶颈   | 耗时证据、选中分支和前后对照；无剩余问题则无需额外改造 |
| E    | 完成功能与性能回归 | 关键矩阵、类型/定向测试、同环境指标                    |
| F    | 清理诊断并复查差异 | 无正式逐帧日志、无越界修改、交付记录                   |

每个阶段只解决当前问题，完成后简要记录改动和下一阶段入口。测试出现新的真实回归时先修复，再推进。出现基础设施阻碍时继续不依赖它的工作，并明确剩余验证缺口。

性能门槛和关键交互已满足后停止扩展。若只有源码修复和单测完成，应交付“实现完成，运行性能尚未验证”；若实际指标仍失败，应交付具体未解决瓶颈，不能写“已解决掉帧”。

按当前风险规则，此 Renderer 局部修复通常由同一会话自测并交付，不默认要求新会话独立验收。用户另有要求或范围演变触发风险规则时再处理。
